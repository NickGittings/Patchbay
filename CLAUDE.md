# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Prerequisites: Rust (edition 2024, via rustup), Node 20+.

```sh
# Desktop app (Tauri 2 + React)
cd apps/desktop && npm install
npm run tauri dev

# CLI (no UI) — useful for exercising core logic quickly
cargo run -p patchbay-cli -- detect .                  # suggested component map for a dir
cargo run -p patchbay-cli -- context patchbay-core     # agent briefing for a component
cargo run -p patchbay-cli -- plan crates-patchbay-core --dir . # planner briefing for a highlighted set

# Checks (run all before considering work done)
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo nextest run --workspace                          # or `cargo test --workspace` (install: cargo install cargo-nextest --locked)
(cd apps/desktop && npm run check)                     # tsc -b + oxlint src + prettier --check + vitest run
(cd apps/desktop && npm run smoke:all)                 # every smoke script against one build, then a pass/fail summary
(cd apps/desktop && npm run smoke)                     # one script: opens the app, drives a pop-out window, exits 0/1
(cd apps/desktop && npm run smoke:views)               # view switching, local planner lifecycle, changes and review
(cd apps/desktop && npm run smoke:git)                 # watcher signals and idle Git refresh behavior
(cd apps/desktop && npm run smoke:tasks)               # task worktrees on a scratch repo (smoke/tasks-fixture.sh)
(cd apps/desktop && node scripts/smoke-all.mjs views git --bail)  # a subset, stopping at the first failure

# Single test
cargo test -p patchbay-core context::tests::claude_gets_neighbour_dirs_and_context
cargo test -p patchbay-core detect                     # all tests matching "detect"
```

Rust unit tests live in `#[cfg(test)] mod tests` at the bottom of each core module (`.config/nextest.toml` caps the process-spawning ones). Frontend unit tests (Vitest, node environment) sit beside pure modules as `src/**/*.test.ts` and run in `npm run check`; mock `../store` and Tauri APIs rather than testing components. Values hashed or encoded on both sides (`sessionId`, `componentLabel`) are pinned to the same golden strings in a Rust and a TS test, so change both together. The smoke scripts are the end-to-end checks: in debug builds only, `src-tauri/src/smoke.rs` evaluates `$PATCHBAY_SMOKE_SCRIPT` in every window and exits 0/1 when the script emits `PASS…`/`FAIL…` on `patchbay://smoke-report`; `src/lib/smoke.ts` exposes the store and helpers as `window.__patchbaySmoke` (dev bundles only). Every `smoke:*` entry runs through `scripts/smoke-all.mjs`, which owns the per-script table (fixtures, roots, extension folders): it builds sessiond, the desktop app and the CLI once (the same build `tauri dev` makes), serves one Vite on 1420 (it refuses to start if anything already answers there, so stop `tauri dev` first), and runs scripts one at a time, each in its own process group so an interrupt reaches the app and the launcher still stops its service. `PATCHBAY_SMOKE_PREBUILT` makes the launchers (`smoke.mjs`, `lifecycle.mjs`, sharing `scripts/smoke-lib.mjs`) start `target/debug/patchbay-desktop` instead of `tauri dev`. Smoke runs stay in the background on macOS: `smoke.rs` makes the app `ActivationPolicy::Prohibited` (wry activates the app for every new webview) and disables WebKit's background throttling, without which long waits in `git.js`/`status.js` stall — on the main window, which `setup` builds from `tauri.conf.json` (`create: false`) for that reason, and on pop-outs, which the backend's `window_open` builds. Consequently no smoke window ever has focus (`document.hasFocus()` is false, focus events never fire), so terminal authority claims, focus-driven `terminal_seen` and the Git refresh on focus aren't covered end to end; don't write smoke checks that wait on them. Default smoke tests use the tracked portable map and files in `apps/desktop/smoke/fixtures/project`, copied into a fresh temporary Git repository per test; the ignored personal map at the checkout root never affects these runs. Explicit fixture roots keep their own maps. Each script runs through `scripts/smoke.mjs`, which gives each run a fresh temporary `PATCHBAY_STATE_DIR` (so no saved workspace or session service leaks between runs or into `~/.patchbay`) and shuts that run's service down afterwards. Never add test hooks that run in release builds.

## Lints and style

- Workspace lints (`Cargo.toml`): `unsafe_code = "forbid"` (the desktop adapter copies them with `deny` so macOS-only `writing_tools.rs` can allow the Objective-C calls that turn Writing Tools off), clippy `all` plus `cast_possible_truncation`/`cast_possible_wrap`/`cast_sign_loss` as warnings, and CI-style clippy runs with `-D warnings` — so these casts must be handled (`try_from`, or a targeted `#[allow]`). Public fallible fns carry `# Errors` / `# Panics` doc sections and pure getters `#[must_use]`.
- Frontend: Prettier (no semicolons, single quotes, width 100, trailing commas), oxlint with react/typescript plugins.
- `.editorconfig`: 2-space indent, 4 for `.rs`, LF.

## Architecture

Three Cargo workspace members plus a React frontend:

- `crates/patchbay-core` — all real logic, UI-agnostic (driven by the desktop app, the CLI, or a future server).
- `crates/patchbay-cli` — thin wrapper over core.
- `apps/desktop/src-tauri` — thin Tauri adapter: each `#[tauri::command]` in `src/lib.rs` maps to one core call. Keep logic out of here.
- `apps/desktop/src` — React 19 + React Flow canvas + xterm.js + zustand.

### Data flow: the frontend owns the project

The backend is stateless with respect to the project map. Terminal processes and their backlogs live in the separate `patchbay-sessiond` helper (`session.rs`), which the desktop reaches through `service::Bridge` (pooled loopback connections, one ordered writer for keystrokes and resizes); the desktop keeps, per open project (`AppState.projects`, keyed by the local project id), core-owned file access, a Git watcher and the active task's worktree (`ProjectAccess { access, watcher, task_root }`): the project's root (chosen in the backend's `open_project` picker) and the external folders the user vouched for (`AccessSnapshot.granted`: folders picked in a backend-run dialog — `add_folder`, `pick_component_folder` — or external folders of a loaded `patchbay.json` that the user allowed in the dialog `open_project` shows; until then those components are "locked", returned in `Opened.locked`). File commands (`list_dir`, `reveal_path`, `resolve_path`) take paths relative to the root and may read only the root plus external component folders on the map that lie within `granted`; the frontend's `sync_roots` (debounced and ordered after component path changes, `App.tsx` and `lib/access.ts`) can narrow that set but never widen it. Grants refresh the current map even when its paths are unchanged; `patchbay://file-access` tells open file trees to retry. Filesystem checks run on snapshots without holding the access lock; the adapter dispatches synchronization, briefing and launch work to blocking workers. All access checks compare canonical paths (so symlinks can't widen them), and no granted folder may contain the project root (`model::check_component_dir`). Every command that takes a `Project` replaces its root with the backend's (`AccessSnapshot::trust`); commands that launch or brief (`terminal_start`, `plan_start`, `component_context`, `plan_context`) also drop locked components (`AccessSnapshot::restrict`), and the git commands (`git_status`, `git_changes`, `git_diff`, `git_review`) skip folders that aren't readable. `rescan_project`/`add_folder` return only what they added (`Added`), which the frontend appends to its current map. The zustand store (`src/store.ts`) holds the map as React Flow `nodes`/`edges`, and `toProject()` rebuilds a full `Project` that is passed to every command that needs it (`terminal_start`, `component_context`, `save_project`, `rescan_project`). `dirty` tracks unsaved edits.

The service outlives the app, so an upgraded build may find one of another `session::PROTOCOL` still running. `Client::ensure` then retires it in its own protocol (`retire_outdated`: the `Hello` handshake and `Request::Shutdown` keep the same wire format in every version, pinned by `retire_wire_format_is_stable`) when it has no running work; otherwise the error reaches the frontend and `TerminalPane` offers "Stop older sessions" (`service_retire` ↔ `serviceRetire`, which ends that work). `patchbay-cli sessions shutdown` retires a service of any version the same way.

### Keeping Rust and TS in sync

Types are mirrored by hand — there is no codegen:

- `crates/patchbay-core/src/model.rs` / `events.rs` / `devices.rs` (serde, `camelCase`) ↔ `apps/desktop/src/types.ts`
- Tauri command list in `src-tauri/src/lib.rs` (`generate_handler!`) ↔ wrappers in `apps/desktop/src/lib/ipc.ts` (Tauri converts camelCase args to snake_case params)
- The terminal event channel name `patchbay://terminal` appears in both `service.rs` (`TERMINAL_EVENT`) and `ipc.ts`.
- The Git invalidation channel `patchbay://git-dirty` appears in both `lib.rs` and `ipc.ts`.
- `status::{SessionStatus, AgentReport, AgentState}` ↔ the same names in `types.ts`; `TerminalEvent::Status` ↔ the `status` event.
- `pty::Snapshot` ↔ `TerminalSnapshot`, `files::DirEntry` ↔ `DirEntry`, `git::{ChangedFile, ChangeKind, FileDiff, Review, Affected, Worktree}` ↔ the same names in `types.ts`. Terminal `started`/`exited` events and snapshots carry `startedMs`/`exitedMs`.
- `model::{MERGE_SCOPE, REVIEW_SCOPE}` ↔ the same constants in `types.ts`; `reviews::{ReviewRequest, Findings}` ↔ `ReviewRequest`/`ReviewFindings`; `review_agent_start`/`review_read`/`review_prune` ↔ `reviewAgentStart`/`reviewRead`/`reviewPrune`; `session::Metadata.branch` ↔ `SessionRecord.metadata.branch`.
- `model::PLAN_SCOPE` ↔ `types.ts` `PLAN_SCOPE` (reserved `"@plan"` scope), `model::PROJECT_SCOPE` ↔ `types.ts` `PROJECT_SCOPE` (reserved `"@project"` id for changed files no component contains).
- Session ids are opaque hashes of project id, component id and terminal key (`workspace::session_id`, `model::task_session_id` ↔ `types.ts` `sessionId(c, t, task?, projectId?)`); a task's terminal key is `{terminalId}@task-{taskId}` (`model::task_terminal`/`TASK_SEPARATOR`). Never parse an id: the service records `Metadata` (project, component, terminal, task) beside it, and the frontend's `sessionMetadata` map backs `parseSessionId`, `sessionTask` and `retask`.
- `tasks::{Task, TaskDraft, TaskPatch}` ↔ the same names in `types.ts`; `task_*` commands ↔ `task*` wrappers in `ipc.ts`; `patchbay://tasks` (pop-out broadcast) lives only in `windows.ts`.
- `context::Kickoff::{ImplementPlan, FixFindings}` ↔ `types.ts` `Kickoff` (`{ kind, reviewSession? }`) in `taskRootStart`/`startTerminal`; `taskRootStart` sends `kind` as `kickoff` and the review's session id as `reviewSession`. Only a `fixFindings` root launch receives review findings, instead of the shared plan and proposal, and its scope is the whole map rather than the highlights. A kickoff launch rejects whenever it doesn't start (closing, a session reset), so a handoff never reports success for an agent that isn't running. `review_fix_task` ↔ `reviewFixTask`.
- `plan_read`/`plan_write` ↔ `planRead`/`planWrite` (`plans::Plan` ↔ `PlanText`; `plan_write` replaces the file only while it holds `expected`); `terminal_start`/`component_context` take optional `peers` (`lib/plan.ts` `peersFor`).

Changing a model field or command means updating both sides.

### Core modules

- `reviews.rs` — validates whole-branch review jobs at `@review`, covering committed changes since the chosen merge base, uncommitted and untracked work. Read-only behavior relies on the briefing. Providers may still require their own permission to write findings under `.git`, even with `--add-dir`. Findings and branch/HEAD/base/start sidecars live under `<git-common-dir>/patchbay/reviews/` with collision-safe branch slugs. Only that folder is added to the writable directories; review sessions can coexist with Implementation. Reads cap text at `plans::PLAN_LIMIT` (`plans::read_capped`) and invalidate older findings on a new review attempt; `prepare` records the attempt before launch and the adapter launches through `Prepared::launch`, which rolls back (`Attempt::rollback`, serialized and skipped once a later attempt replaced the sidecar) only when the service certainly refused it (`Bridge::start_reporting`/`call_reporting`; a lost reply keeps the new attempt), and a review's base may not be its own branch. Resuming a review session finds its artifact through `Metadata.branch` (public session summaries strip the launch environment) and records a new attempt (`resume_attempt`) unless its HEAD and worktree are unchanged, and refuses once the branch is no longer checked out there. `read` reports `edited_since_start` from a `git status` of the branch's whole worktree (`git::changed_since`; a deleted file counts its folder's mtime). Review sessions record their branch in `Metadata.branch`; the panel reads that branch's findings when shown, on focus and review exits, and polls them while its Findings toggle is open. A fix is resolved from the review session's own record in the backend (`reviewed`: its worktree, which `git::worktrees` must still list, and recorded branch; `fix_task`: the non-missing task holding that worktree, else the project folder when it is the open worktree's top). `handoff(root, reviewed)` inlines up to `HANDOFF_LIMIT` of the findings as a "Review findings" briefing section with branch, base, saved age, freshness and a file reference if cut, and refuses a launch outside the reviewed worktree, once the branch is no longer checked out there, or without findings. Only the fresh root agent started with `Kickoff::FixFindings` receives it. No reviews folder is granted (`--add-dir` is writable, and a fix session must stay resumable), and ordinary launches and resume roots stay unchanged. `review_prune` (called once when Review opens, best-effort) drops findings of deleted branch refs. Removing a task together with its worktree deletes the branch's findings best-effort, unless another worktree has the branch checked out; forgetting a task keeps them. Findings paths are built inside the canonical reviews folder, the same one agents get with `--add-dir`. Owned `review-` briefings follow the `merge-` retain/Forget lifecycle. Merge briefings point to findings, identify matching HEADs, and ask the agent to report unresolved issues without fixing them unless needed for the merge.

- `model.rs` — `Project`/`Component`/`Link`/`TerminalSpec`. Persisted as `patchbay.json` at the repo root; `root` is absolute in memory but never serialized (portable file). A `Link` means `source` depends on `target`; `Project::neighbours` returns both directions as `Relation::DependsOn`/`UsedBy`. Bump `SCHEMA_VERSION` for format changes. `Project::dependents` walks `UsedBy` transitively to find the components a change may affect (each with the changed components it depends on).
- `detect.rs` — walks the repo for `package.json`, `Cargo.toml`, `pyproject.toml`, `requirements.txt`, `go.mod`; infers kind, task terminals (dev/test/etc.), links from inter-package deps, and a layered layout. Nested git repos without a manifest still become components. `merge_new` only adds components for folders not already in the project (compared after resolving symlinks, `model::resolve_dir`) and appends them — it must never touch user edits. `detect_folder` (Add repo…) detects a picked folder with paths relative to the project root (`../sibling` for a repo outside it); it rejects the root and any folder containing it. `rescan` = root plus the given external folders (the external component folders themselves, never their enclosing repo, so a monorepo isn't swept in). Ids come from `slug`, which never returns an empty string.
- `context.rs` — `component_context` builds the markdown briefing; `session_spec` turns a terminal into a `SessionSpec`. For `agent` terminals it atomically writes the briefing to the platform temp directory under `patchbay/<name>-<root hash>-<scope>.md` (unique per project root, so open projects and worktrees never share one) and sets `PATCHBAY_CONTEXT_FILE`. `command_tokens` lexes the command once in the syntax of the shell that runs it (POSIX quoting on Unix; on Windows cmd's double quotes only, with `'`, `^` and unquoted operators treated as compound), and Claude and Codex are recognised by program basename (including quoted paths, Windows extensions, and leading `env`/assignments), leaving compound shell commands alone while accepting quoted operators in arguments. On Unix and Windows, both adapters append `--add-dir` for each neighbour; Claude receives `--append-system-prompt-file` (its `--settings`/`--setting-sources` are left alone; status hooks are opt-in user hooks, see `agent_hooks.rs`), while Codex receives `-c developer_instructions=<TOML string>`, prefixed with the user's own instructions (a `-c` in the command, else the selected profile's or the top-level value in `$CODEX_HOME/config.toml`) so they aren't replaced. On Windows the TOML string encodes shell-sensitive characters, parentheses included, as Unicode escapes; on Unix it is a plain TOML string inside single quotes. Arguments use platform quoting; generated Windows paths containing percent signs are inserted from private environment variables to avoid recursive expansion. Unsupported non-interactive Codex subcommands keep their original command and show a briefing notice. If the full Codex command exceeds `CMD_BUDGET` on Windows (cmd's 8191 UTF-16 units measured after `%VAR%` expansion, less room for npm/pnpm shims) or 120 KiB on Unix (below Linux’s per-argument limit), its instructions become a short pointer to the briefing file. `SessionSpec.notice` explains that fallback, a compound command or an unrecognised agent, naming the context variable in the shell's own syntax; successful injection stays quiet. All terminals get `PATCHBAY_COMPONENT` (and, from `pty.rs`, `PATCHBAY_STATUS_FILE`). The `Policy` check runs here, before spawn (currently `AllowAll`).
- `pty.rs` — `PtyManager` spawns commands via the user's login shell (`$SHELL -ilc`, or `-il` for an empty command = interactive shell) so PATH matches their terminal when launched from the dock; Windows runs `cmd.exe /V:OFF /S /C` directly for commands without double quotes; commands with them go through an encoded, constant PowerShell bootstrap that launches cmd with raw command text from a private environment variable, avoiding portable-pty’s MSVC re-quoting of shell syntax; empty commands open interactive `powershell.exe`. The bootstrap inherits terminal I/O and returns the command’s exit code. Stopping a Windows session kills its whole process tree (`taskkill /T /F`). `spawn` reserves the id in `starting` and creates the process without holding the `sessions` lock, so other sessions' I/O isn't blocked. Before reading process output, `spawn` appends any `SessionSpec.notice` as a dim `[patchbay]` line to the backlog and emits it through the same sequenced `Output` path, so snapshots and pop-outs replay it; the notice also rides on the `Started` event and `Snapshot`, and `TerminalPane` shows it as a dismissible banner, since full-screen agents hide the dim line. Per session: one reader thread emitting `Output` events, one waiter thread emitting `Exited` (exit code normalized: success → 0, failure → ≥1). Remembers last size per session id across restarts. Each session id also keeps a `Backlog` (last 512 KB of output, total byte count `end`, `generation` bumped on every spawn, running/exit code) that outlives the process; `snapshot()` returns it (data base64-encoded on the wire) so a newly opened window can replay output it missed. `Output` events carry `seq` (byte offset) and all events carry `generation` (globally increasing) so consumers can de-duplicate against a snapshot. Session ids aren't project-scoped, so opening a project calls `reset()` (`terminal_reset`, also run on app exit), which hangs up everything, drops all backlogs, waits up to `RESET_GRACE` for the processes (tracked as `orphans`) and then kills their process groups, and returns a generation floor; the frontend's `resetSessions(floor)` clears its caches and ignores late events at or below it. Backlogs also record wall-clock start/exit times (Unix ms, the clock file mtimes use), so the review view can tell whether a task ran after the latest edit.
- `status.rs` — what a session is doing (`SessionStatus`): output activity (echo of input excluded), an agent's self-reported `AgentState` (working / needs input / review / idle) read from the file named by `PATCHBAY_STATUS_FILE` (first line a state word, then optional JSON such as a Claude Code hook's stdin; a reported `working` with no output or report for 15s counts as idle; typing an answer turns `needsInput` into `working`, and Esc or Ctrl+C turns it or `working` into `idle`, also when typed before the monitor read the report, judged by the file's mtime; only repeated `working` reports keep their `sinceMs`), and for task terminals only (`SessionSpec::service`) a local `http(s)` URL or bare `host:port` printed (skipping lines about proxies, databases or errors; a later address replaces one whose port hasn't answered) or the `readyWhen` text (`ready`) plus a TCP probe of that port (`healthy`, false after two failures). It also carries `stopped` (set by `PtyManager::kill`, so a stop isn't a failure) and `seenMs` (`PtyManager::mark_seen` via `terminal_seen`, broadcast as a status event so every window agrees). Native provider hooks (`agent_hooks.rs`, opt-in via Tools → Agent status integration, which installs `patchbay-sessiond report-status <provider>` as a user hook) take precedence: agent terminals get a private per-generation journal (`PATCHBAY_REPORT_DIR`, with `PATCHBAY_REPORT_SESSION`/`_GENERATION`/`_PROVIDER`; other terminals get none, and inherited values are cleared) that the reporter appends sequenced events to; `Tracker::on_hook` accepts only this session's generation, the current conversation (a `SessionStart` from `resume`/`clear` switches it; a fresh `startup` in another conversation is a nested `claude -p`/`codex exec` and is ignored), and the current turn. Authoritative reports don't go stale, but Esc turns a native `needsInput` into an unconfirmed `idle` and native `working` into unconfirmed work that goes stale, since providers send no hook for an interrupt or a denial. Each `PtyManager` creates a fresh owner-only temp folder for its sessions' status files (one per generation, removed on exit/reset, the folder on drop); one monitor thread (250ms) reads changed status files outside all locks, schedules probes and emits `TerminalEvent::Status` only on meaningful change; the waiter reads the file one last time and emits a final status before `Exited`, both under the backlog lock the monitor emits under, so no status follows an exit. `Snapshot` carries the current status.
- `events.rs` — `TerminalEvent` (`started`/`output`/`exited`/`status`) and the `EventSink` trait; Tauri implements the sink by emitting to the webview.
- `devices.rs` — terminal presets. Built-ins in `/devices/*.device.json` are compiled in via `include_str!` (add new ones to the `BUILTIN` list too); user presets in `~/.patchbay/devices/` override built-ins by id.
- `files.rs` — `list_dir` for the pop-out file tree: dirs first, hides only `.git` (not detection's `SKIP_DIRS`), and hides symlinks resolving outside the roots; `resolve` rejects paths escaping every root. Roots are the project root plus external folders (`../billing`), and must already be canonical: they are never resolved again, so a root later swapped for a symlink can't redirect listings. Nested roots are deduplicated. Paths in and out are relative to the project root.
- `git.rs` — `status` groups components by containing repo (`group_by_repo`, nearest `.git`), runs `git --no-optional-locks status --porcelain=v2` once per repo (in parallel threads, fsmonitor off, literal pathspecs limited to the members' folders unless one sits at the repo root, so a project inside a large repo doesn't scan all of it; callers pass only canonical, allowed folders), and attributes each file to the most specific component (`owner_of`); nested repos aren't counted by their parent. Files under the project root that no component contains go to the reserved `PROJECT_SCOPE` (`with_project_scope`, skipped when a component sits at the root), so root files like `CLAUDE.md` still show up as "Project files". Also reports the repo name for components outside the project root's repo. The main window refreshes on project/component-path and access changes, window focus, terminal exits, and debounced filesystem changes (`lib/git.ts`); requests are coalesced and stale results discarded. Pop-outs receive the resulting badges through the existing `patchbay://git` broadcast. For review, `changes` lists each component's files (paths relative to the project root, with `ChangeKind`, mtime and added/removed line counts from one `diff --numstat` per repo; untracked files are counted once per size/mtime) attributed the same way, and each path once (a staged deletion wins over the same path untracked); `component_changes` queries only the one component's repo, `review` adds `Project::dependents` of the changed components, and `diff` returns a file's diff against `HEAD` (untracked files against `/dev/null`, the empty tree before the first commit), capped at `MAX_DIFF_BYTES`. `diff` only accepts paths `changes` lists for that component (checked with a `git status` limited to that path and the rename's old path), so it can't read arbitrary files, and always passes `--no-ext-diff --no-textconv` so a repo's config can't make it run commands. All git invocations go through `git()` (fsmonitor off, no optional locks). `worktrees` lists the project repo's worktrees; `in_worktree` maps the root and in-repo components into one of them (only paths `worktrees` returned), which core `review`/`diff` accept as an optional `worktree` (passed through by `git_review`/`git_diff`) so Review can show another worktree's changes (polled while shown, since the watcher only covers the open one).
- `watch.rs` — core-owned background watcher with a 1s debouncer, watching only roots inside a Git repo. FSEvents/Windows get one recursive watch per outermost root (FSEvents restarts its stream on every added path); inotify/kqueue register directories individually so ignored trees consume no watches. Ignore rules are cached per repo (`Rules`: one `ls-files -oi --directory` plus `ls-files -ci` per load, then batched `check-ignore --stdin` for unknown event paths and their parents); tracked paths stay observable under ignored directories. Rule files, `info/exclude`, config and the global excludes file (mtime checked every 5s) reload the rules; an index change only rescans when its ignored-but-tracked files changed. Unreadable or vanished directories are skipped; only failed watches mark coverage incomplete, which refreshes status every 5s and retries with backoff (30s–5min). Missing roots are polled every 1s for their return, without status polling. New root sets refresh once their coverage is registered. `GitWatcher::update` replaces a worker that died. Shutdown signals cancellation without waiting for traversal. Linked worktree metadata (`.git` files) is not resolved yet, so commits there may wait for focus or terminal exit.

### Plan handoff

`plans.rs` — the plan a planner hands to implementation agents: one Markdown file per task (`main` without one) at `<git-common-dir>/patchbay/plans/<task>.md` (`tasks::store_dir`, beside `tasks.json`; task ids are checked so they can't escape the folder), written atomically and capped at `PLAN_LIMIT` (`read` cuts longer files at a character boundary and says so); `tasks::remove` deletes the task's plan, best-effort. The planner belongs to the project, not a worktree: its sessions, plan (`main`) and proposal stay put when the active worktree changes (`captureLaunch` forces `task = null` for `PLAN_SCOPE`; `plannerSessionId` always uses that scope, and `plan_start`/`plan_context` and their IPC wrappers no longer accept a task), and Plan's Implement (`lib/planHandoff.ts`) hands them to the active worktree — offering a new worktree first on the project folder — by applying the proposal there (`proposals::apply(from, to)`, which preserves a saved plan newer than the pending proposal while applying its assignments and keeps the planner's own plan in step) or copying the nonempty project plan. An empty project plan must fail Implement even if the worktree has an older plan. Implement saves editor drafts before applying assignments, stops the planner, and starts a fresh root agent with an implementation prompt; launch failures propagate back to Plan, and the view switches to Implementation only after launch succeeds. Cancelling the New worktree dialog clears its pending follow-up callback. A pending proposal's components are outlined on Plan's canvas (`proposedScope`, UI only). Planner sessions get `PATCHBAY_PLAN_FILE` and a briefing line asking them to write the agreed plan there, plus `--add-dir` for the plans folder, created beforehand (`plans::dir`) and always added because agent sandboxes keep `.git` read-only unless it is a writable root itself; outside a repo the briefing leaves the line out. `session_resume` accepts the existing plans folder (`plans::existing_dir`, never created by the check) for any session. The Plan view's "Saved plan" editor reads and writes the same file, keeps unsaved planner edits per project at module level (so leaving the view keeps them), saves through `plans::write_if` and asks for a second Save when the planner rewrote the file since it was loaded, won't edit a cut plan, and is saved before Implement briefs agents. When an agent terminal starts (`terminal_start`, and the `component_context` preview), the adapter's `handoff_sections` adds "Shared plan" (`plans::section`: says when the plan was saved and whether it was cut) and "Working alongside" (`context::peers_section`: the other highlighted components and their links with this one, when the highlighted set holds it and others; pop-outs receive the highlighted set with `patchbay://tasks`); component agents also get `--add-dir` for those peers and, with a plan, the plans folder (`context::session_spec_with`). `briefing_sections` puts these backend-owned sections (and the task's) whole ahead of the extension context, which alone counts against `CONTEXT_BUDGET`. Neither changes session ids.

Claude’s opt-in status integration also captures native plans from `ExitPlanMode` hook payloads (`agent_hooks::plan_signal`), without reading provider-supplied paths or approving its dialog. `PreToolUse`/`PermissionRequest` capture a presented plan; `PostToolUse` records approval. A later turn event withdraws an unapproved presentation, restoring the previous plan only if the presented text is still current; editor changes are preserved. `plans::capture`/`withdraw` serialize these writes with the plan editor and proposal apply. Status is journaled first, then the hook uses a short bridge timeout so a disconnected desktop cannot hold up Claude. The bridge accepts captures and withdrawals only from a planner and checks its provider conversation to reject nested runs; subagent events are ignored. Repeated captures of unchanged text retain applied assignments.

### Graph actions

`actions.rs` — groups (`Project.groups`) and terminal roles (`TerminalSpec.action`) drive `ActionPlan` (start a group's development tasks in startup stages, or validate the components a change may affect) and `GraphActions` (one coordinated operation at a time; environments owned per project, group and task). They run inside the session service (`Request::ActionRun`/`ActionStopGroup`/`ActionCancel`) through the `Terminals` trait, so their terminals are ordinary recorded sessions; the adapter's `graph_action_*` commands only trust, restrict and move the project into the task's worktree first. Results and the busy state land in the project they ran for (`patchProject`, `lib/actions.ts`).

### Worktrees

`tasks.rs` — a task is a named piece of work on its own branch and worktree of the project repo, sharing the map. Tasks are per user, stored in `<git-common-dir>/patchbay/tasks.json` (shared by every worktree, never committed); `list` reconciles `branch`/`missing`/`current` with `git::worktrees`. `create` validates the branch (`check-ref-format`, no leading `-`) and base, then runs `git worktree add [-b]` into a free sibling folder `<repo>-<slug(branch)>` (the webview never picks the path); `attach` takes only a path `git::worktrees` lists; `remove` runs `git worktree remove` without `--force` (git refuses dirty trees) and keeps the branch; the frontend stops the task's terminals first. `create` checks the store is readable before running git and removes the new worktree (and branch) again if saving fails. Hot paths look tasks up with `stored` (no `git worktree list`), since `in_worktree` validates the path anyway. `project_in` moves a trusted, restricted `Project` into the task's worktree via `git::in_worktree`, dropping components outside that repo (and failing for required ones); `context_section` tells agents which task, branch and worktree they work in. The adapter's `for_task` looks the task up in the backend store (the webview sends only its id) for `terminal_start`, `plan_start`, `component_context` and `plan_context`, which then use `context::session_spec_for`/`plan_session_spec_for` (task in the session id and briefing file name) with extension sections read from the worktree; `git_status`/`git_changes` take `task`, `git_review`/`git_diff` the worktree path. `task_*` commands take the project id; `task_activate` adds that project's active task worktree to its watcher roots (`ProjectAccess.task_root`). Resuming a task's session re-checks its folders against the task's worktree. Extension terminals and the pop-out file tree still use the open worktree.

Frontend: `tasks`/`activeTask` are per-project UI state (`ProjectState`, never `dirty`) and `newTask` is global; `lib/tasks.ts` loads the list when a project's tab opens (`refreshTasks`), and `followActiveTask` (main window) calls `task_activate` per project, and clears and refreshes Git badges only when a project switches task (not on tab switches). Every terminal list keys sessions with the active task (`TerminalPane`/`ValidationChips` take an explicit `task` override; extension terminals use `null`); `startTerminal(c, t, task?)` defaults to it. Attention lists every task's sessions and `revealTerminal` switches task. `WorktreePicker` (a `Popover`, the dialog base `Menu` builds on) in Plan’s Planner scope header, Implementation’s header and the toolbar in Navigation and Review opens an overview of the Project folder and listed worktrees: labels and branches, attention, About component chips, changed and may-affect components via `git_review`, running terminals, collapsed editable notes, Review and Remove. `NewTaskDialog` ("New worktree": new branch or existing worktree, seeded from highlights, else the selection, by `lib/tasks.ts` `seedNewTask`) lives beside it in `components/tasks/`; Plan also offers "New worktree…". Clicking another worktree's row (outside its controls, chips, path and remove confirmation) switches to it; its title button is the keyboard way in; the trigger marks the active worktree's attention and, separately, other worktrees'. UI text calls these worktrees; internal task types, commands and storage names stay the same. Review defaults to the active task's worktree and shows validation chips for any worktree with a task.

### Frontend terminals

`lib/terminals.ts` keeps one long-lived xterm instance per session id in a module-level registry and re-parents its DOM element on `attach`, so scrollback survives tab switches and restarts. `lib/sessions.ts` applies backend `TerminalEvent`s to both the store (running/exit code → node health) and the xterm, skipping bytes already covered by a snapshot (`seq`/`generation`). `hydrateSession` buffers live events, replays `terminal_snapshot`, then drains the buffer. `components/TerminalPane.tsx` is the shared xterm host used by the dock and pop-out tiles.

`lib/display.ts` `terminalStatus` turns a terminal's kind and `SessionState` (including `status`) into a health class, label and detail used by node chips, dock tabs, grid tiles, inspector rows and planner tabs (`components/status/StatusLabel.tsx`). A finished review or a failure asks for attention (`unseenSince`) until a focused window shows the session (`TerminalPane` calls `terminal_seen`). Components showing relative times call `useClockTick` (`lib/clock.ts`) to re-render every 10s. `lib/attention.ts` ranks what wants the user (needs input > failed > not responding > review) for the toolbar's `AttentionMenu` and per-component `AttentionPill`s (both counting extension-started terminals, `componentTerminals`); `revealTerminal` opens the planner tab (`planActive`, UI only), the Navigation dock for extension terminals, or the Implementation tile.

### Views

The main window switches between Navigation (hierarchy and canvas; the inspector while `showsInspector` — the per-project `inspector` (opened or closed by the user) or else an existing selected component or link — and the dock while `dockTabs` lists running sessions (plus exited ones in `dockKept` — revealed with `setActiveSession`, failed, or exited while active — until closed there) or a dock extension view exists, both in `lib/panels.ts`; hidden panels collapse rather than unmount, so their tabs keep their state, since react-resizable-panels can't add a panel to a mounted group and the canvas must not remount, and reopen at the size remembered under `panels['App-open']`), Plan (highlighted canvas above a project-level planner dock, with a worktree picker in Planner scope), Implementation (a header worktree picker and an ordered component list with a visibility flag per entry, reached with Plan's "Implement →"; click a pill to toggle its visibility, × to remove it from Implementation, and "Add component…" to append one; Plan highlights update the same list and unhighlighting retains a hidden pill; each component's tiled terminals with an "+ Add terminal…" select that saves to the map, a header "Agent in each" that reuses or adds an agent preset per component (`lib/implement.ts`, presets from `lib/plan.ts` `agentDevices`), a per-tile maximize and × that asks for confirmation, waits for pending launches/restarts and stops every worktree copy before removing the saved terminal, and a pop-out button on each component's header; `revealTerminal` sets the UI-only `revealed`, which shows its component after the highlighted ones without joining them and un-maximizes other tiles), and Review (every changed component's files and diffs, plus project files, filterable by component chips and switchable between worktrees; the components that may be affected, and whether each one's task terminals ran since the change: `ReviewView.tsx`, `lib/review.ts`). Review offers “Review branch…” then “Merge into…”, with both sessions in `ReviewAgentPanel` (`lib/reviewAgents.ts`, reserved `@review`/`@merge` scopes). Review sessions have a read-only Findings toggle; the title reports whether findings cover HEAD and every uncommitted change in the reviewed worktree made before the review started (`Findings.edited_since_start`, computed in core, so the status never depends on Review's change list). Review bases include local branches (`git_branches` ↔ `gitBranches`). Findings refresh on focus and review exit, and every 5s while shown (Review's source branch, or while the panel's Findings toggle is open); the merge dialog reports their status without blocking. Hide/Show agents, Sessions and Attention recover either scope without moving the active task or adding a Navigation dock tab. Panel layout ids remain `ReviewView-merge` and `ReviewView-merge-terminal`. Fixes stay in Implementation: a finished review with nonempty saved findings offers "Fix in Implementation →" (`lib/reviewHandoff.ts`), which asks the backend for the review's task (`review_fix_task`, `null` for the project folder, selected exactly), activates it, and starts a fresh root agent with a preset of the reviewer's provider (session records keep no preset id), else `agentDevices`' first. The button waits while any review of that worktree may still be writing (`reviewWorktreeBusy`: running and reporting `working`, or without a report, producing output), since interactive reviewers keep running at their prompt. Only that agent receives the findings of the reviewed branch and the fix prompt; the view switches after launch succeeds if the user is still in that worktree, and unknown worktrees must first be added as tasks. `lib/diff.ts` parses a patch into hunks with old/new line numbers for `DiffView`. The shared pieces live in `components/changes/`; `ChangesPanel` also backs the pop-out's Changes tab. Change lists and diffs reload whenever the store's `gitChanges` object is replaced, which happens on every Git refresh. `view`, `highlighted`, `implementationComponents` (ordered ids and visibility), and `planStartedWith` are persisted in the per-user workspace layout; they never change `dirty` or `patchbay.json`. Plan terminals come from agent devices and use the reserved `@plan/<terminalId>` session scope. `plan_start` / `plan_context` in the Tauri adapter ↔ `planStart` / `planContext` in `lib/ipc.ts`; `context::plan_session_spec` launches at the repo root with the scoped briefing (Claude and Codex also get `--add-dir` for in-scope or nearby components outside the root), while `policy::Scope` supplies either a component or the planner's real component set to policy checks. `TerminalGrid` is shared by Implementation and component pop-outs. Navigation, Plan, Implementation and Review use ⌘1–4; a saved `tasks` view falls back to Navigation. All views use the same session and xterm registries, preserving scrollback and window ownership.

### Component windows

Each component can open in a native window labelled `component-<hex-encoded id>` that loads `index.html?component=<id>`, built by the backend's `window_open` (so macOS gets a Writing Tools-free webview configuration, as the main window does); `main.tsx` routes that to `ComponentWindow` (Files/Changes tabs + every terminal tiled). Every webview is a separate JS context with its own store and xterm registry. The main window stays the owner of the project: a pop-out emits `patchbay://popout-ready`, and `lib/windows.ts` answers with `patchbay://project` and `patchbay://git`, re-broadcasting (debounced) on edits; pop-outs apply it with `syncProject`, which keeps session state. Closing the main window closes all pop-outs (`lib.rs` `on_window_event`), and opening another project closes them too. Terminal events go to the main window on `patchbay://terminal` and to a pop-out only on `patchbay://terminal/<its label>` (`service::Bridge::route`; `component_window_label` must match `componentLabel` in `windows.ts`, and `showsSession` filters which records a window hydrates). A session can be shown in several windows at once; `windows.ts` tracks the last-focused window across webviews, and a pane claims the session's authority (`terminal_attach` with `claim`, which types and sizes the PTY) when its window becomes visible or active, never on plain resizes (xterm `onData` only writes from visible, attached panes, and replayed output never replies). New window labels must match `component-*` in `capabilities/default.json`.

### Extensions

- `crates/patchbay-core/src/extensions.rs` validates local manifests (`engines.patchbay`), isolates
  errors, persists disabled ids (disabled extensions claim no contribution ids; enabling one whose
  ids an active extension holds is refused), installs folders, serves extension assets
  (`asset_request`/`read_asset`, capped at `ASSET_LIMIT` while reading), checks permissions
  (`Registry::allowed`), stores per-extension JSON, builds ad-hoc terminals (`command_terminal`,
  `run_terminal`, launched with `context::extra_session_spec`), and assembles all extension context
  (`Registry::sections`: file sections read through `files::resolve`, then provider sections, within
  one `CONTEXT_BUDGET`, since `claude` gets the briefing as an argument). Keep this logic in core.
  The adapter's `Extensions` loads the `Registry` on first use, always on a blocking worker.
- `extensions.rs` contribution/registry types and `context.rs::ContextSection` ↔ `src/types.ts`;
  maintain these Rust/TS mirrors by hand. `packages/extension-api/index.d.ts` is the author API.
- `devices::load_devices(&Registry)` orders builtin < extension < user. `detect_with`,
  `detect_folder_with`, and `rescan_with` take extension detectors; original wrappers remain.
  All context/session builders now take `&[ContextSection]`.
- Backend commands ↔ `lib/ipc.ts`: `list_extensions`, `set_extension_enabled`, `reload_extensions`,
  `install_extension`, `reveal_extensions_dir`, `command_run`, `extension_terminal_run`,
  `extension_storage_get`, `extension_storage_set`, `extension_file_read`. Terminal/context
  commands accept optional `extraContext` for code providers, added to core-owned file sections.
  The frontend collects it only for agent terminals and briefings (`extensions/context.ts`);
  pop-outs ask the main window over `patchbay://context-request`/`-reply`, so every window gives
  an agent the same briefing. Extension commands, file I/O and the `patchbay-ext` protocol run
  off the main thread.
- `src/extensions/host.ts` owns hidden opaque-origin extension frames in the main window only.
  Source-bound JSON-RPC checks manifest permissions and limits sizes/concurrency/rate. A timed-out
  call only fails; a host is stopped after `MAX_TIMEOUTS` consecutive timeouts or a protocol
  violation. Calls made during an extension's own activation never wait on it. `terminals.run`
  names its session after the command, so repeats reuse it (at most `MAX_RUN_TERMINALS` per
  extension), and never takes the dock's focus. Hosts hear map edits debounced and without
  position-only changes. `bootstrap.js` is compiled into the backend's `patchbay-ext` protocol HTML; don't inject
  Tauri into it. The protocol only serves enabled extensions to the main webview and resolves
  assets canonically inside their folders. The IPC boundary is Tauri's invoke key, injected into
  top frames only (frames can reach `window.webkit.messageHandlers.ipc`; the smoke probe forges
  it); the null-Origin rejection is defense in depth. Keep capability remote origins absent. Visible views use separate sandboxed, CSP-restricted frames.
- `when.ts` parses declarative clauses without eval. `whenContext.ts` fetches filename sets through
  `list_dir`. Runtime extension terminals, badges, and rendered view HTML live only in UI state.
  Ad-hoc commands never mutate `patchbay.json`. Reload/disable/project switch disposes code hosts.
- `npm run smoke:extensions` uses `PATCHBAY_EXTENSIONS_DIR=examples/extensions` and the Docker
  fixture, checks contributions, palette launches, context, badges, views, iframe IPC denial
  (fetch and forged postMessage) and `terminals.run` reuse.
  Existing pop-out and view smoke checks must continue passing. Smoke handles stay debug-only.
