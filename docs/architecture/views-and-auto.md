### Views

Auto mode (`lib/auto.ts`, `components/auto/`) is a per-worktree frontend controller: plan → implement → validate → review ⇄ fix → merge gate → merge (or Done, for a run in place). Light/Standard/Thorough presets set the fix budget, severity floor and validation; Advanced overrides and ask/automatic merge are chosen per run. Each agent stage launches its own preset (`AutoRun.agents`, else `device`, the only one older runs record; `agentFor`), seeded in the dialog from the global agent roles; the implement stage still hands off the plan stage's planner. With several reviewers (`AutoRun.reviewers`), the review stage launches them in one round (`startReviewAgents`), tracks the first and owns the rest (`laneSessions`, stopped when the stage ends, on Stop, Skip and settling); its completion waits while another reviewer still works, before judging the combined verdict. Every session a run tracks is an `AutoLaunch` (session id, start time, launch request, review lane, turn): the primary in the run's `session*` fields, reviewers beside it in `laneSessions`; `launches`/`track` convert between them, so a reviewer taking the lead just moves to the front. Auto owns a launch while its process generation is the one it launched: its start time, else its launch request is still its record's latest (`owns`), and `stopOwned` rechecks that as it stops each one. `startReviewAgents` always sends a round id (also for one reviewer) and returns each started reviewer's session id, request id and lane (`started`), adopting after its one reconciliation a start whose lost reply the backend couldn't recover yet; the run records them and `reviewRound`. `observe` judges every tracked session the same way for the drive and Resume (failed: forgotten, stopped, relaunched, or exited or idle before finishing its turn; asking for input counts as being in a turn, and only the reviewer an input wait opened counts as stopped while it waits), and `roundStatus` classifies Auto's round from those and the findings, matched by lane: `superseded` when the latest round isn't `reviewRound` (someone started a newer review), `broken` when a reviewer failed before writing or an untracked launch was never confirmed, `complete` once every reviewer finished its turn or failed after writing, else `running`. The drive pauses on a superseded or broken round with what to do, and stops tracking reviewers that failed after writing, also during an input wait (it follows a tracked agent while the run is running or waiting on you; Pause or Stop end that). Resume (refused while the session service is disconnected) keeps a running or complete round's reviewers that still work. It ends a broken round: it stops the round's reviewers it owns and infers the stage again, so it reviews anew, but asks the user to close any it can't prove it started instead. A superseded round stops only what Auto owns; the newer review's sessions stay and inference follows them. A review launch the service refuses with `session::TERMINAL_RUNNING` (↔ `types.ts` `TERMINAL_RUNNING`, matched by exact text) pauses rather than failing the run. It can infer the next stage from manual work, pauses for input or interruptions, and requires installed authoritative status hooks. `TaskWorkspace.auto` is UI state in the workspace layout, never `patchbay.json` or `dirty`; every unfinished restored run is Paused until Resume, its explicit scheduled trigger, or an eligible autonomous startup continuation (done, stopped and failed runs stay so) and keeps tracking, and owning, the agent it launched, which outlives the app in the service. A task's inferred goal comes from its own plan only. Every worktree, including the main checkout, owns its planner and plan. Only an explicit project-draft handoff transfers plans and history into a new worktree; ordinary creation, attachment and the Auto dialog's New worktree… button do not inherit project drafts. A start of a terminal a run still tracks sends the run's recorded brief (`AutoRun.sessionBrief`, and a planner's `plan` kickoff, whose resume command drops its prompt) so Restart's fingerprint matches. The plan stage finishes only once its worktree plan or proposal differs from when the planner launched (`planMark`). A new run on a branch whose earlier work is already merged plans its goal instead of ending as Done; the dialog previews with the same inference. Automatic merge needs a HEAD whose current findings leave nothing to fix at the run's severity floor (`mergeableHead`); otherwise the merge gate asks, and skipping a fix whose budget ran out goes there too. An agent whose stage didn't finish (an incomplete merge, an unreadable verdict) stays running and tracked for the user. Validation runs through `lib/actions.ts` `graphActionIn` and pauses when the backend refuses it. A run records its branch (`AutoRun.branch`) when it starts and judges only that branch: when its worktree has another one checked out, a running run pauses and the approval wait reports it. The approval wait shows merge-status errors in `AutoRun.gateError`, never in its reason, and keeps retrying. A merge agent that ends, is stopped or forgotten, while waiting or not, first checks Git, so a merge finished by hand ends the run Done; every path that finds the branch integrated (`settleIntegrated`) also stops an owned agent still running, since a finished run offers no Stop. Start is refused only while a launch may still attach its agent; a drive of a stopped run acts only on its own `runId`. Snapshots read `merge_outcome` only while merging or inferring the stage of a reviewed or merged branch (a fresh branch is trivially an ancestor). Auto reviews against the merge destination when it is a branch, resolves the project folder to the current worktree, and treats the planner as its own only while planning or tracking it. Validation without a validation terminal is skipped, not failed. Validation failures (`AutoRun.validationFindings`) keep a review from reaching the merge gate until a validation passes or the user skips validation; while they remain, finished work and resumed changed branches go to Validate whatever the effort's validation setting, and skipping or resuming an interrupted fix keeps them. A fix round counts once its launch returns a session, even if confirming it fails. The main window's `followAuto` watches raw agent reports and polls findings; updates are pinned through `patchTask`, and launches pause when the worktree is not driveable (see [Scheduler](scheduler.md)). Review completion requires a fresh structured verdict, and merge completion is checked in Git. `smoke:auto` uses a fake agent writing hook journals, findings, a fix commit and a real merge on scratch worktrees. Every stage Auto launches and still owns is recorded in its worktree's chat with `origin: 'auto'` and its run id (`recordStageLaunch`), so Chat and the Review view show it like any other launch. The Auto panel's strip is the shared Plan → Build → Review → Merge `StageStrip` (`autoStepper`); once work outside an ended run starts, it shows that work's stages instead, under a note. The Review view shows the same strip above its controls, makes the next step's button primary (Fix, or Merge into… when the model offers a merge), says when Auto or the chat's lead is driving, and shows only the shown worktree's reviewers and merges. The Plan view shows the strip, defaults to the running planner's tab, and makes Implement primary once a plan is ready.

Auto launch controls in Full and Simple mode expose two independent, default-off toggles:
**Autonomous execution** (`AutoRun.autonomous`, also saved in dialog drafts and the backend
`AutoBrief`) and **Merge automatically after review** (`merge.mode`). Autonomous runs can launch
while another worktree is selected as long as their project remains open. Their briefing tells
agents to make reasonable decisions, resolve routine problems and save required artifacts while
preserving command permissions. Full mode uses Standard effort with Advanced overrides. Simple mode
uses Light effort with a configurable fix budget. Clearing Fix rounds while editing keeps the last
valid value. Both modes can select either merge setting. A Chat lead's `startAuto` uses the same
mode default unless the request explicitly sets an effort.

The existing controller serializes autonomous recovery with launching and scheduling. It recovers
missing plans, unreadable review artifacts, incomplete stages and interrupted owned sessions.
Before recovery it reconciles service records and checks process ownership, the source branch and
competing agents. Confirmed conversational prompts receive a task-specific continuation through
`terminal_prompt`, which checks generation, authority and hook-confirmed readiness again in the
service; `needsInput` and pending approvals remain blocked pauses, with no terminal approval text.
Otherwise recovery stops only owned processes and relaunches. Optional scanner, Builder and
Sub-builder jobs receive the same autonomous briefing in their persisted provider run. Recovery uses
the provider's stable request identities, continues owned conversational prompts through a guarded
`continueJob` control and `terminal_prompt`, and retries failed jobs while retaining submitted
reports, assignments and isolated Sub-builder checkouts. Persisted `recovery` records the
stage, required artifact fingerprint, attempt count, action identity, timestamp and a pending
relaunch reservation. Polling and restart cannot submit the same prompt twice. A completed stage
or changed required artifact resets the budget; resetting sessions or review round IDs does not.
Three attempts without progress fail the run with the unresolved reason. Pause and Stop invalidate
in-flight recovery, and the panel and activity log show decisions, attempts and exhausted budgets.

Recovery cannot increase the configured fix-round limit: autonomous runs fail when blocking
findings or validation failures remain at that limit. Automatic merge requires a current, covered
review at the severity threshold and required validation for the current HEAD and file modification
fingerprint (`validationHead`/`validationMark`). Changes after review return autonomous execution to
validation/review. Merge preparation in core also checks `MergeRequest.expectedSourceHead`,
so a commit made during asynchronous frontend preflight cannot bypass the reviewed HEAD.
With automatic merge disabled, execution waits at Ready to merge for approval.

Auto offers every other local branch as a merge destination. The dialog and the Chat lead's
`startAuto` request default to the open checkout's branch when eligible, then local `main` or
`master`. Start rejects an explicit destination that is missing or is the source branch. When
inferring the next stage of previously reviewed or merged work, Auto checks integration even if
the destination has no checkout, so the dialog can leave an already integrated goal blank. The
merge stage and approval wait use the same fallback to recognize a merge done by hand. Before
resolving the destination checkout, Auto refreshes task ownership and checks that the run can
still launch and no other Auto run holds the checkout. Resolution uses the same path as manual
merges, and Auto publishes task changes once it returns (see [Worktrees](worktrees.md)).

A worktree with no branch to review against, the project folder on its default (`main`/`master`)
or only branch (not a detached HEAD), runs Auto in place: plan → implement → validate → review ⇄
fix → Done, with no merge gate or merge. `autoSnapshot` falls back to the current HEAD as the base
for a run not started yet (`AutoSnapshot.inPlace`), and Start records it as `AutoRun.baseCommit`
and `IN_PLACE_MERGE`, which every later review of the run compares against (the backend accepts a
commit id wherever it takes a review base, `reviews::prepare` and `git::review`). Uncommitted work
present at Start is part of the first review, since reviews include the worktree's changes. A clean
review, skipping a review, or skipping the wait on an exhausted fix budget ends the run Done
(`afterReview` gives each run's stage after review); an autonomous run whose fix budget runs out
fails, as any run does. Clean findings of an unchanged HEAD start a new goal of a run in place at
Plan instead. In-place runs refuse to start at Merge or Ready to merge and never read
`merge_outcome`; restore keeps `baseCommit` only when it is a full commit id (`isCommitId`), so a
malformed one leaves a run that fails Resume with `NoReviewBase`. The dialog shows "Runs in place
on <branch>, reviewing against <short sha>, no merge." in place of the merge settings
(`MergeFields`), still offers New worktree…, and reloads when a Git refresh changes what the base
was judged from or the HEAD it shows (`reviewBaseMoved` against a `JudgedBase`), so a new commit
updates the sha and a checked-out feature branch or attached base switches it back to merging. The
run panel drops Merge from its stage strip and Merge now, and in place of the destination and merge
mode says the run is in place with no merge and which commit it reviews against. Findings and other
views show a commit as a short sha (`lib/commitId.ts`). Task worktrees and project folders on
another branch still need a destination and merge; one with no base at all still fails with
`NoReviewBase`, as does a started run without `baseCommit`. A run whose worktree checks out
another branch pauses (`BranchMoved`) as before.
Startup continuation and explicit schedule precedence are described in [Scheduler](scheduler.md).

#### Agent preset compaction

Set compaction overrides in the agent preset's command; role assignments and `AutoRun.agents` let plan, implement, review, fix and merge use different presets. `context::decorate_agent` preserves Claude's `--settings` and Codex `-c` overrides when adding the briefing; `context::codex_review_command` also keeps the compaction override in native reviews. Claude's `-c` means `--continue`, not a configuration override.

- Claude (POSIX shell): `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=60 claude`. Patchbay recognises the leading variable assignment. If a Claude settings file sets the same variable under `env`, it can replace the inherited value; use `claude --settings '{"env":{"CLAUDE_AUTOCOMPACT_PCT_OVERRIDE":"60"}}'` for a session override of user/project settings. See [Claude environment precedence](https://code.claude.com/docs/en/env-vars#precedence) and [settings precedence](https://code.claude.com/docs/en/settings#settings-precedence); managed settings still take priority.
- Claude (Windows): Patchbay runs preset commands through `cmd.exe`, so the POSIX assignment and single-quoted JSON above do not work. Save `{"env":{"CLAUDE_AUTOCOMPACT_PCT_OVERRIDE":"60"}}` in a JSON file, then use `claude --settings "C:\agent-presets\compact-60.json"`, replacing the example with the file's absolute path so it works in every worktree.
- Codex (POSIX and Windows): `codex -c model_auto_compact_token_limit=120000` is an example for a model with a 200000-token context window. Choose a token count for the selected model, leaving headroom below its context limit for tool results and output; this number is not a percentage or a universal recommendation. See the [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

For long-lived, resumed plan and implementation sessions, consider an earlier threshold, such as 50–60% of the context window, to reduce input tokens per subsequent turn. Compaction summarizes the transcript and can lose file details; it also rebuilds the cached conversation prefix, so compacting more often is not a cache-retention strategy or a guarantee of lower total cost. See [Claude's prompt cache statistics](https://code.claude.com/docs/en/costs#prompt-cache-statistics).

Leave provider defaults for review, fix and merge unless there is a measured reason to tune them. [Claude's override can only lower the threshold](https://code.claude.com/docs/en/env-vars#variables); values above its default are ignored. For Codex, keep any override safely below the selected model's context window so compaction can run before context is exhausted. These overrides need no dedicated Patchbay setting.

Compaction trims a running conversation. Finished work is handled separately: see stage retirement and task completion in [Chat mode](chat-mode.md).

### Navigation presentation

The navigation rail defaults to compact (52px). Its bottom toggle saves optional labels
(168px) in `patchbay.railExpanded`; unavailable local storage falls back to in-memory state.
Windows narrower than 1100px temporarily render compact without overwriting that preference.
Expanded navigation separates Views, Mode and Tools. Expanding never changes view or Chat state.
Utility-panel width bounds account for the actual rail width, and pointer resizing measures
from the rail's rendered right edge. Rail tooltips wait 350ms on pointer entry and appear
immediately on keyboard focus; exit, blur, click, Escape and unmount cancel pending tooltips.

Review groups task/branch and comparison context with verdict and findings above its file list;
the full worktree path is disclosed on demand. Review and component Changes use `PanelStatus`
for loading and retryable failures, with technical details collapsed. Validation remains scoped
to each component rather than being implied by the review verdict.
