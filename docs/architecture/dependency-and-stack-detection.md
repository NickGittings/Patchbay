### Dependency detection

`link_proposals.rs` — after the first save of a map with an unlinked component (`lib/mapSave.ts` `onMapCreated`, `lib/dependencies.ts`), the frontend runs `detect_links` (`maintenance::new_links`: Rescan's link proposals between components already on the map) and reviews what it finds, else offers the agent; Project → Detect dependencies…, the Project panel and the search command open the same offer. "Not now" sets the per-project `dependencyPromptDismissed` (workspace layout, never `patchbay.json` or `dirty`). The agent is a job agent at `MAP_SCOPE` (`context::job_agent_spec`, owned `map-` briefings), launched by `map_agent_start` with the agent command token; its preset id is recorded in `Metadata.lane` so Restart (`lib/sessions.ts` `mapPreset`) launches the same one, never the recorded command. Its token (`LaunchContext.role`, `agent_bridge::Role::Mapper(Proposes::Links)`, which the adapter's `authenticate` derives from the session's scope and terminal like `Role::Planner`; `Role::of`) may only read context and status and submit `agent propose-links` (`Action::ProposeLinks`, validated against the readable map; the briefing has it pipe the JSON to `--file -` so it writes no file), stored per project root under `~/.patchbay/map-links/`; `patchbay://map-links` and opening a project tab show the review (`DependencyDialog`). Dialogs are kept per project (`useDependencies.dialogs`) and only the active project's shows, so one never blocks another project's; a closed project's is dropped. Map recovery and external-save conflicts defer submissions and block dependency edits, including an already-open review; pending submissions remain available after recovery. Scans and clears count as busy per project (the first save's scan too, which fills an unscanned offer opened meanwhile). A detection launch already on its way keeps its preset and tab (`sessions.ts` `launching`), and only a started session is revealed. Accepted links are an ordinary map edit with `detection.detector: "agent"`, which Rescan never offers to remove. Accepting links (`addDependencies`) also lays the whole map out by dependency (`lib/layout.ts` `arrange`: dependents left, foundations right, the grid of `detect::layout`, rows ordered by barycenter sweeps, unlinked components below, anchored at the map's top-left) through `lib/arrange.ts` `arrangeMap` → `store.moveComponents`, an ordinary edit; the toast offers Undo (`MessageAction`) and `Canvas` tweens the moved nodes and fits the view (`onArranged`). Project → Arrange map and the palette run the same layout on demand. Each submission has a unique `Pending.id`; `map_links_clear` takes that id and keeps a newer submission, and the frontend clears before closing the review, never reopening a cleared id from a stale read. Its tab shows in Navigation's dock in every worktree, and revealing it never switches worktree.

### Stack detection

`stack_proposals.rs` — the agent at `MAP_SCOPE` with terminal `stack_proposals::STACK_TERMINAL` (↔ `types.ts` `STACK_AGENT_TERMINAL`), beside dependency detection's, so it shares its dock, reveal and restart handling (`dependencies.ts` `startDetectionAgent`, which shows a running one even while map edits are blocked, else checks they aren't, and names a run of another preset, and `sessions.ts` `startMapAgent(projectId, preset, terminalId)`, which routes `stack` to `stackAgentStart`). Its `Role::Mapper(Proposes::Stack)` token may read context and status and submit only `agent propose-stack` (`Action::ProposeStack`, validated against the readable map: existing task terminals by id (never Validation ones), or new ones with a name and one-line command that no terminal of the component already has by name (ignoring case and spacing, as the frontend's `sameName`) or slugged id, each with ready text and a reason); neither detection agent may submit the other's proposal, stored per project root under `~/.patchbay/stack-proposals/` (`submissions::Store`, shared with dependency detection's `map-links/`). `stack_proposals::{ProposedTerminal, Pending}` ↔ `ProposedStackTerminal`/`PendingStack`; `stack_agent_start`/`stack_proposal_read`/`stack_proposal_clear` ↔ `stackAgentStart`/`stackProposalRead`/`stackProposalClear`; the `patchbay://stack-proposals` event lives in `agent_commands.rs` (adapter) and `ipc.ts`. `lib/stackAgent.ts` keeps each open project's submission for the Stack panel's review; Apply marks the ticked task terminals Development, never shell, agent or Validation ones (adding new ones unless the component already has a terminal of that name; an empty ready text keeps the terminal's own; when none of the ticked ones still applies, the submission stays and a message says so, and when only some do, a message names the components and terminals left out) and adds their components to the stack of that name (names compared ignoring case and spacing; an existing stack keeps its startup order, and isn't edited when no member is added), an ordinary map edit, then clears that submission id, hiding it locally at once and even when the clear fails, with the review busy until the read that follows, so it can't be applied twice; reads are ordered per project, so a stale one never replaces a newer submission, and a failed read keeps the one shown; the read on opening a project waits until its map edits aren't blocked and is retried at a later project change after failing. `smoke:stack` drives it with a fake agent.
