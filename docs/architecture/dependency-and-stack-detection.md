### Dependency detection

`link_proposals.rs` — after the first save of a map with an unlinked component (`lib/mapSave.ts` `onMapCreated`, `lib/dependencies.ts`), the frontend runs `detect_links` (`maintenance::new_links`: Rescan's link proposals between components already on the map) and reviews what it finds, else offers the agent; Project → Detect dependencies…, the Project panel and the search command open the same offer. "Not now" sets the per-project `dependencyPromptDismissed` (workspace layout, never `patchbay.json` or `dirty`). The agent is a job agent at `MAP_SCOPE` (`context::job_agent_spec`, owned `map-` briefings), launched by `map_agent_start` with the agent command token; its preset id is recorded in `Metadata.lane` so Restart (`lib/sessions.ts` `mapPreset`) launches the same one, never the recorded command. Its token (`LaunchContext.role`, `agent_bridge::Role::Mapper(Proposes::Links)`, which the adapter's `authenticate` derives from the session's scope and terminal like `Role::Planner`; `Role::of`) may only read context and status and submit `agent propose-links` (`Action::ProposeLinks`, validated against the readable map; the briefing has it pipe the JSON to `--file -` so it writes no file), stored per project root under `~/.patchbay/map-links/`; `patchbay://map-links` and opening a project tab show the review (`DependencyDialog`). Dialogs are kept per project (`useDependencies.dialogs`) and only the active project's shows, so one never blocks another project's; a closed project's is dropped. Map recovery and external-save conflicts defer submissions and block dependency edits, including an already-open review; pending submissions remain available after recovery. Scans and clears count as busy per project (the first save's scan too, which fills an unscanned offer opened meanwhile). A detection launch already on its way keeps its preset and tab (`sessions.ts` `launching`), and only a started session is revealed. Accepted links are an ordinary map edit with `detection.detector: "agent"`, which Rescan never offers to remove. Accepting links (`addDependencies`) also lays the whole map out by dependency (`lib/layout.ts` `arrange`: dependents left, foundations right, the grid of `detect::layout`, rows ordered by barycenter sweeps, unlinked components below, anchored at the map's top-left) through `lib/arrange.ts` `arrangeMap` → `store.moveComponents`, an ordinary edit; the toast offers Undo (`MessageAction`) and `Canvas` tweens the moved nodes and fits the view (`onArranged`). Project → Arrange map and the palette run the same layout on demand. Each submission has a unique `Pending.id`; `map_links_clear` takes that id and keeps a newer submission, and the frontend clears before closing the review, never reopening a cleared id from a stale read. Its tab shows in Navigation's dock in every worktree, and revealing it never switches worktree.

### Stack detection and configuration

`stack_proposals.rs` owns stack detection briefings and proposal validation. The agent runs at `MAP_SCOPE` with terminal `STACK_TERMINAL` (`types.ts` `STACK_AGENT_TERMINAL`), beside dependency detection. `startDetectionAgent` / `startMapAgent` route it through `stack_agent_start`; the optional `stackId` selects a stack by stable id for **Detect again**. The briefing includes existing terminals, commands, readiness, membership, ordering and timeout. It asks for repeatable preparation, builds and actual app launch in Development commands, chained with `&&`, relative to the selected worktree. Separate `worktreeSetup` remains optional, reviewed preparation for new worktrees, not a stack-start hook. Missing tools, credentials and manual steps belong in proposal reasons.

The `Role::Mapper(Proposes::Stack)` token may read context and status and submit `agent propose-stack`, but cannot execute environments or edit configuration. Neither detection agent may submit the other's proposal. Proposals are stored per project root under `~/.patchbay/stack-proposals/` (`submissions::Store`), and surfaced through `patchbay://stack-proposals` and `stack_proposal_read`. Existing task terminals are identified by id and may include a replacement `command`; new terminals require a unique name and command. Shell, agent and Validation terminals cannot become stack services. Version 1 proposals without `stackId` retain the older additive, name-matching behavior and preserve existing readiness when an empty ready text accompanies no command change.

`lib/stackAgent.ts` applies reviewed proposals as ordinary map edits without executing commands. A proposal with `stackId` replaces that stack's name, ordering and complete membership, preserving its id and timeout. Existing terminal ids are reused, commands can be corrected, and empty readiness clears a faulty wait. Development terminals omitted from the replacement, including those on removed components, lose their startup role but retain their saved definitions. Terminal configuration is shared across stacks and the Inspector; review explains that consequence and lists resulting members, changed commands/readiness and removals. A removed target or invalidated terminal prevents the entire replacement before edits. Discard leaves configuration intact. Applying clears only the reviewed submission id; stale reads cannot reopen it and newer submissions remain available.

The Stack rail also creates stacks, chooses components, edits task terminal names, commands and readiness, adds custom Development terminals and removes terminals from startup. It uses the same store edits and map persistence as the Inspector. Changes to running terminals take effect after Stop and Start. Start uses the existing graph action engine in the selected worktree, including dependency ordering, readiness waits, failure rollback, repeated-start reuse and shared-terminal ownership. Configuration stays shared across worktrees. `smoke:stack` covers detection, cancellation, replacement, manual configuration, persistence and launches in two worktrees; `smoke:actions` covers ordering and readiness end to end.
