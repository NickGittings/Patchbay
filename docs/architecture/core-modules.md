### Core modules

- `usage.rs` — local Claude/Codex subscription windows; each provider reports its own error (`Usage.claude_error`/`codex_error`), so one unreadable configuration never hides the other. Codex reads bounded tails of the newest session logs (walking `YYYY/MM/DD` newest first). Parsed log tails are cached by path, length and mtime, and resets are rounded to the minute so relative Codex resets keep one alert identity. Opt-in Claude capture wraps the user status line with `patchbay-sessiond status-line <usage dir>` (the folder argument, absent in older installs, lets the reporter find its capture and chain whatever Claude's environment says), preserving its command and stdin and running it with `/bin/sh` as Claude does (Git Bash, else cmd, on Windows); it never chains another Patchbay reporter (by executable name, and at run time through `PATCHBAY_STATUS_LINE_CHAINED`), and a chained line that fails or prints nothing leaves Patchbay's own line. Expired windows never gate Auto. The rail Usage panel owns capture setup and thresholds; `lib/usage.ts` polls, warns once per reset/level, and gates each Auto stage before launch. Thresholds live in workspace settings; capture and cached Claude data live under the machine-local `usage/` directory.

- `reviews.rs` — validates whole-branch review jobs at `@review`, covering committed changes since the chosen merge base, uncommitted and untracked work. Claude presets receive a normal prompt invoking the code-review skill with `high <chosen base>...HEAD`, followed by a review of staged, unstaged and untracked work and a findings write; prose is not passed as skill arguments. Codex presets use non-interactive `codex exec --sandbox read-only review --base <base commit> -o <lane findings file>` with read-only and final-report instructions, replacing preset sandbox, approval, bypass and working-directory flags with a read-only sandbox and no escalation. Native review targets use a verified base commit id, keeping cmd-sensitive branch names out of bare arguments. Generated findings paths and Claude prompts containing percent signs use private environment arguments on Windows. Codex receives the complete review and Auto briefing through its developer instructions, with a file pointer for large briefings; its scope and reporting instructions consistently exclude untracked files and let the CLI save its final message. Other programs and unsupported/compound commands keep Patchbay’s review briefing. `Started.native` records the native style (absent in older sidecars); `Saved::read` converts Codex’s final `[P0]`–`[P3]` report through `from_codex` to `[critical]`–`[low]`, keeping its parsed verdict alongside the text in a bounded cache keyed by file stamp, style and read limit (complete reports are reused whenever they still fit the new limit), so combining, findings cards and Fix/merge handoffs share the same format. The frontend findings parser accepts native reports’ absolute file references, normalizing Windows separators for Review’s existing suffix matching. Empty/missing, incomplete or unrecognized native output supplies no verdict; explicit native no-findings conclusions can establish clean on complete reports. Truncated reports retain readable prefix verdicts and counts, and Codex tags are still normalized. Previous findings retain their recorded style, defaulting to Patchbay when no earlier sidecar exists. Codex’s base-branch review excludes untracked files; files present at launch or read time (the same Git status scan as `edited_since_start`, `git::review_coverage`) set `Findings.uncovered` (↔ `ReviewFindings.uncovered`), which keeps the findings current but blocks Auto's automatic merge (`mergeableHead`). Its notice explains this. `SessionSpec.rerun_on_resume` reruns the recorded command without conversation history, independent of its argument layout, and like a conversation resume refuses once its briefing file is gone; since the rerun names the launch's base commit, `Started.base_commit` records it and `resume_attempt` measures the new attempt's merge base from it. Codex tags are rewritten outside code, and a no-findings conclusion reads as clean only when no prose line hedges it (`but`, `however`, `except`…); quoted code never reads as an error. Claude Resume drops the appended skill prompt as for other jobs. Read-only behavior relies on the briefing for Claude and other CLIs; Codex review explicitly enforces a read-only sandbox even for write-capable presets. Providers may still require their own permission to write findings under `.git`, even with `--add-dir`. Findings and branch/HEAD/base/start sidecars live under `<git-common-dir>/patchbay/reviews/` with collision-safe branch slugs. Only that folder is added to the writable directories; review sessions can coexist with Implementation. Reads cap text at `plans::PLAN_LIMIT` (`plans::read_capped`) and invalidate older findings on a new review attempt; `prepare` records the attempt before launch and the adapter launches through `Prepared::launch`, which rolls back (`Attempt::rollback`, serialized and skipped once a later attempt replaced the sidecar) only when the service certainly refused it (`Bridge::start_reporting`/`resume_reporting`; a lost reply keeps the new attempt). Every `Bridge` launch, restart and resume recovers a lost reply itself by listing sessions for its request id (`Bridge::recovering`, looking until a two-second deadline and stopping at the first failed list); session summaries (`Service::summaries`, `SessionRecord.requestIds`) list a launch's request id only once its process spawned (`Service.spawning`, the one launch spawning under the `operation` lock), so a launch still spawning, which may yet fail and be rolled back, stays uncertain, and a review's base may not be its own branch. Resuming a review session finds its artifact through `Metadata.branch` (public session summaries strip the launch environment) and records a new attempt (`resume_attempt`) unless its HEAD and worktree are unchanged, and refuses once the branch is no longer checked out there. `read` reports `edited_since_start` from a `git status` of the branch's whole worktree (`git::changed_since`; a deleted file counts its folder's mtime). Review sessions record their branch in `Metadata.branch`; the panel reads that branch's findings when shown, on focus and review exits, and polls them while a review of that worktree is busy (`reviewWorktreeBusy`) or its Findings toggle is open, re-reading as soon as the reviews settle. A fix is resolved from the review session's own record (`reviews::Session`: its cwd and recorded branch, read from the service by the adapter's `recorded_review`, never from the webview). `fix_task` makes `handoff`'s checks first (the cwd's worktree still has the branch checked out, and nonempty findings, checked without reading their freshness), so a refused fix changes nothing in the UI, and that HEAD resolves, then returns the stored task holding that worktree (`tasks::stored_at`), else `None` when the project folder is its top; neither lists worktrees. `handoff(root, session)` inlines up to `HANDOFF_LIMIT` of the findings as a "Review findings" briefing section with branch, base, the reviewed HEAD (or that they predate the latest attempt), a note that later commits and edits may address some, and a file reference if cut (read the complete report from the beginning, since native normalization and UTF-8 boundaries make inferred offsets unreliable), and refuses a launch outside the reviewed worktree, once the branch is no longer checked out there, or without findings. Only the fresh root agent started with `Kickoff::FixFindings` receives it. No reviews folder is granted (`--add-dir` is writable, and a fix session must stay resumable), and ordinary launches and resume roots stay unchanged. `review_prune` (called once when Review opens, best-effort) drops findings of deleted branch refs. Removing a task together with its worktree deletes the branch's findings best-effort, unless another worktree has the branch checked out; forgetting a task keeps them. Findings paths are built inside the canonical reviews folder, the same one agents get with `--add-dir`. Several agents can review a branch in parallel: each gets a `ReviewRequest.lane` (its preset id, recorded in `Metadata.lane` for resume), its own session slot and findings file (`<branch name>~<lane identity>.md`), and they share a `round` id in their sidecars. `read`, `fix_task` and `handoff` cover the reviewers of the latest round (the round of the most recently started attempt; sidecars from before rounds stand alone): the text is combined with a heading per reviewer, the verdict is `combined` (issues if any reviewer reports issues, the largest count per severity, none until every reviewer has one), `reviewed_head` is set only once every reviewer wrote findings for the same HEAD, and `reviewers` reports each one's progress. A reviewer whose file is missing counts as one still writing. Until some reviewer of the latest round writes, the text shown and handed off is the most recently written earlier round's findings, whichever reviewers (lane set) wrote them, marked as an earlier attempt; a lane the latest round reused still holds the findings of the attempt it replaced, which its sidecar names (`Started.previous`: that attempt's round and base), so they count toward that round. The handoff retains its established `4 * plans::PLAN_LIMIT` budget to preserve existing fix briefings; missing, empty and unreadable reports do not take a share from written findings; whitespace-only reports consume at most their own byte length. Files are stamped first to select the shown round; its files are then opened, sized from those same handles and read within their allocated shares, so a report written since the first stamp is not read with a stale zero-byte budget; `Findings.base` is that shown text's base, while `round` (the latest round's id, ↔ `ReviewFindings.round`), `reviewers`, `verdict` and `reviewed_head` describe the latest round. `remove`/`prune` cover every lane. Owned `review-` briefings follow the `merge-` retain/Forget lifecycle. Merge briefings point to findings, identify matching HEADs, and ask the agent to report unresolved issues without fixing them unless needed for the merge.

- `model.rs` — `Project`/`Component`/`Link`/`TerminalSpec`. Persisted as `patchbay.json` at the repo root; `root` is absolute in memory but never serialized (portable file). A `Link` means `source` depends on `target`; `Project::neighbours` returns both directions as `Relation::DependsOn`/`UsedBy`. Bump `SCHEMA_VERSION` for format changes. `Project::dependents` walks `UsedBy` transitively to find the components a change may affect (each with the changed components it depends on).
- `detect.rs` — walks the repo for `package.json`, `Cargo.toml`, `pyproject.toml`, `requirements.txt`, `go.mod`; infers kind, task terminals (dev/test/etc.), links from inter-package deps and from manifests pointing into another component's folder (`Manifests::refs`, from the manifests detection already read and parsed: requirements `-r`/`-c`/`-e` and local paths, `file:`/`link:` packages, Cargo/Poetry/uv path deps (never `[workspace.dependencies]`), Go `replace`, Gradle `includeBuild`/`projectDir` outside comments; never to a component containing the source), and a layered layout. Single-root (`detect_with`) and combined-root (`detect_roots_with`, used by Rescan and dependency detection) scans share the dependency resolver; all permitted roots contribute candidates before links are resolved, since Rescan offers to remove builtin links the scan no longer finds. Nested git repos without a manifest still become components. `merge_new` only adds components for folders not already in the project (compared after resolving symlinks, `model::resolve_dir`) and appends them — it must never touch user edits. `detect_folder` (Add repo…) detects a picked folder with paths relative to the project root (`../sibling` for a repo outside it); it rejects the root and any folder containing it. `rescan` = root plus the given external folders (the external component folders themselves, never their enclosing repo, so a monorepo isn't swept in). Ids come from `slug`, which never returns an empty string.
- `context.rs` — `component_context` builds the markdown briefing; `session_spec` turns a terminal into a `SessionSpec`. For `agent` terminals it atomically writes the briefing to the platform temp directory under `patchbay/<name>-<root hash>-<scope>.md` (unique per project root, so open projects and worktrees never share one) and sets `PATCHBAY_CONTEXT_FILE`. `command_tokens` lexes the command once in the syntax of the shell that runs it (POSIX quoting on Unix; on Windows cmd's double quotes only, with `'`, `^` and unquoted operators treated as compound), and Claude and Codex are recognised by program basename (including quoted paths, Windows extensions, and leading `env`/assignments), leaving compound shell commands alone while accepting quoted operators in arguments. On Unix and Windows, both adapters append `--add-dir` for each neighbour; Claude receives `--append-system-prompt-file` (its `--settings`/`--setting-sources` are left alone; status hooks are opt-in user hooks, see `agent_hooks.rs`), while Codex receives `-c developer_instructions=<TOML string>`, prefixed with the user's own instructions (a `-c` in the command, else the selected profile's or the top-level value in `$CODEX_HOME/config.toml`) so they aren't replaced. On Windows the TOML string encodes shell-sensitive characters, parentheses included, as Unicode escapes; on Unix it is a plain TOML string inside single quotes. Arguments use platform quoting; generated Windows paths containing percent signs are inserted from private environment variables to avoid recursive expansion. Unsupported non-interactive Codex subcommands keep their original command and show a briefing notice. If the full Codex command exceeds `CMD_BUDGET` on Windows (cmd's 8191 UTF-16 units measured after `%VAR%` expansion, less room for npm/pnpm shims) or 120 KiB on Unix (below Linux’s per-argument limit), its instructions become a short pointer to the briefing file. `SessionSpec.notice` explains that fallback, a compound command or an unrecognised agent, naming the context variable in the shell's own syntax; successful injection stays quiet. All terminals get `PATCHBAY_COMPONENT` (and, from `pty.rs`, `PATCHBAY_STATUS_FILE`). The `Policy` check runs here, before spawn (currently `AllowAll`).
- `pty.rs` — `PtyManager` spawns commands via the user's login shell (`$SHELL -ilc`, or `-il` for an empty command = interactive shell) so PATH matches their terminal when launched from the dock; Windows runs `cmd.exe /V:OFF /S /C` directly for commands without double quotes; commands with them go through an encoded, constant PowerShell bootstrap that launches cmd with raw command text from a private environment variable, avoiding portable-pty’s MSVC re-quoting of shell syntax; empty commands open interactive `powershell.exe`. The bootstrap inherits terminal I/O and returns the command’s exit code. Stopping a Windows session kills its whole process tree (`taskkill /T /F`). `spawn` reserves the id in `starting` and creates the process without holding the `sessions` lock, so other sessions' I/O isn't blocked. Before reading process output, `spawn` appends any `SessionSpec.notice` as a dim `[patchbay]` line to the backlog and emits it through the same sequenced `Output` path, so snapshots and pop-outs replay it; the notice also rides on the `Started` event and `Snapshot`, and `TerminalPane` shows it as a dismissible banner, since full-screen agents hide the dim line. Per session: one reader thread emitting `Output` events, one waiter thread emitting `Exited` (exit code normalized: success → 0, failure → ≥1). Remembers last size per session id across restarts. Each session id also keeps a `Backlog` (last 512 KB of output, total byte count `end`, `generation` bumped on every spawn, running/exit code) that outlives the process; `snapshot()` returns it (data base64-encoded on the wire) so a newly opened window can replay output it missed. `Output` events carry `seq` (byte offset) and all events carry `generation` (globally increasing) so consumers can de-duplicate against a snapshot. Session ids aren't project-scoped, so opening a project calls `reset()` (`terminal_reset`, also run on app exit), which hangs up everything, drops all backlogs, waits up to `RESET_GRACE` for the processes (tracked as `orphans`) and then kills their process groups, and returns a generation floor; the frontend's `resetSessions(floor)` clears its caches and ignores late events at or below it. Backlogs also record wall-clock start/exit times (Unix ms, the clock file mtimes use), so the review view can tell whether a task ran after the latest edit.
- `status.rs` — what a session is doing (`SessionStatus`): output activity (echo of input excluded), an agent's self-reported `AgentState` (working / needs input / review / idle) read from the file named by `PATCHBAY_STATUS_FILE` (first line a state word, then optional JSON such as a Claude Code hook's stdin; a reported `working` with no output or report for 15s counts as idle; typing an answer turns `needsInput` into `working`, and Esc or Ctrl+C turns it or `working` into `idle`, also when typed before the monitor read the report, judged by the file's mtime; only repeated `working` reports keep their `sinceMs`), and for task terminals only (`SessionSpec::service`) a local `http(s)` URL or bare `host:port` printed (skipping lines about proxies, databases or errors; a later address replaces one whose port hasn't answered) or the `readyWhen` text (`ready`) plus a TCP probe of that port (`healthy`, false after two failures). It also carries `stopped` (set by `PtyManager::kill`, so a stop isn't a failure) and `seenMs` (`PtyManager::mark_seen` via `terminal_seen`, broadcast as a status event so every window agrees). Native provider hooks (`agent_hooks.rs`, opt-in via Settings → Agent status integration, which installs `patchbay-sessiond report-status <provider>` as a user hook) take precedence: agent terminals get a private per-generation journal (`PATCHBAY_REPORT_DIR`, with `PATCHBAY_REPORT_SESSION`/`_GENERATION`/`_PROVIDER`; other terminals get none, and inherited values are cleared) that the reporter appends sequenced events to; `Tracker::on_hook` accepts only this session's generation, the current conversation (a `SessionStart` from `resume`/`clear` switches it; a fresh `startup` in another conversation is a nested `claude -p`/`codex exec` and is ignored), and the current turn. Authoritative reports don't go stale, but Esc turns a native `needsInput` into an unconfirmed `idle` and native `working` into unconfirmed work that goes stale, since providers send no hook for an interrupt or a denial. A Codex `PermissionRequest` stays `working` until the terminal's text (outside controls, echo excluded) is quiet for `APPROVAL_QUIET_MS`, since its automatic reviewer may answer it, then asks as `needsInput` from that moment; typing meanwhile keeps unconfirmed work. PTY exit (`Tracker::on_exit`) ends unresolved native work before `Exited`, and the monitor still applies hooks it drained just before the exit. Each `PtyManager` creates a fresh owner-only temp folder for its sessions' status files (one per generation, removed on exit/reset, the folder on drop); one monitor thread (250ms) reads changed status files outside all locks, schedules probes and emits `TerminalEvent::Status` only on meaningful change; the waiter reads the file one last time and emits a final status before `Exited`, both under the backlog lock the monitor emits under, so no status follows an exit. `Snapshot` carries the current status.
- `events.rs` — `TerminalEvent` (`started`/`output`/`exited`/`status`/`activity`/`reply`) and the `EventSink` trait; Tauri implements the sink by emitting to the webview.
- `devices.rs` — terminal presets. Built-ins in `/devices/*.device.json` are compiled in via `include_str!` (add new ones to the `BUILTIN` list too); user presets in `~/.patchbay/devices/` (the state folder's, so `PATCHBAY_STATE_DIR` moves them) override built-ins by id.
- `files.rs` — `list_dir` for the pop-out file tree: dirs first, hides only `.git` (not detection's `SKIP_DIRS`), and hides symlinks resolving outside the roots; `resolve` rejects paths escaping every root. Roots are the project root plus external folders (`../billing`), and must already be canonical: they are never resolved again, so a root later swapped for a symlink can't redirect listings. Nested roots are deduplicated. Paths in and out are relative to the project root.
- `git.rs` — `status` groups components by containing repo (`group_by_repo`, nearest `.git`), runs `git --no-optional-locks status --porcelain=v2` once per repo (in parallel threads, fsmonitor off, literal pathspecs limited to the members' folders unless one sits at the repo root, so a project inside a large repo doesn't scan all of it; callers pass only canonical, allowed folders), and attributes each file to the most specific component (`owner_of`); nested repos aren't counted by their parent. Files under the project root that no component contains go to the reserved `PROJECT_SCOPE` (`with_project_scope`, skipped when a component sits at the root), so root files like `CLAUDE.md` still show up as "Project files". Also reports the repo name for components outside the project root's repo. The main window refreshes on project/component-path and access changes, window focus, terminal exits, and debounced filesystem changes (`lib/git.ts`); requests are coalesced and stale results discarded. Pop-outs receive the resulting badges through the existing `patchbay://git` broadcast. For review, `changes` lists each component's files (paths relative to the project root, with `ChangeKind`, mtime and added/removed line counts from one `diff --numstat` per repo; untracked files are counted once per size/mtime) attributed the same way, and each path once (a staged deletion wins over the same path untracked); `component_changes` queries only the one component's repo, `review` adds `Project::dependents` of the changed components, and `diff` returns a file's diff against `HEAD` (untracked files against `/dev/null`, the empty tree before the first commit), capped at `MAX_DIFF_BYTES`. `diff` only accepts paths `changes` lists for that component (checked with a `git status` limited to that path and the rename's old path), so it can't read arbitrary files, and always passes `--no-ext-diff --no-textconv` so a repo's config can't make it run commands. All git invocations go through `git()` (fsmonitor off, no optional locks). `worktrees` lists the project repo's worktrees; `in_worktree` maps the root and in-repo components into one of them (only paths `worktrees` returned), which core `review`/`diff` accept as an optional `worktree` (passed through by `git_review`/`git_diff`) so Review can show the active task's worktree's changes (the watcher covers the active task's worktree too, so they aren't polled).
- `watch.rs` — core-owned background watcher with a 1s debouncer, watching only roots inside a Git repo. FSEvents/Windows get one recursive watch per outermost root (FSEvents restarts its stream on every added path); inotify/kqueue register directories individually so ignored trees consume no watches. Ignore rules are cached per repo (`Rules`: one `ls-files -oi --directory` plus `ls-files -ci` per load, then batched `check-ignore --stdin` for unknown event paths and their parents); tracked paths stay observable under ignored directories. Rule files, `info/exclude`, config and the global excludes file (mtime checked every 5s) reload the rules; an index change only rescans when its ignored-but-tracked files changed. Unreadable or vanished directories are skipped; only failed watches mark coverage incomplete, which refreshes status every 5s and retries with backoff (30s–5min). Missing roots are polled every 1s for their return, without status polling. New root sets refresh once their coverage is registered. `GitWatcher::update` replaces a worker that died. Shutdown signals cancellation without waiting for traversal. Linked worktree metadata (`.git` files) is not resolved yet, so commits there may wait for focus or terminal exit.

#### Agent preset compaction

Set compaction overrides in the agent preset's command; role assignments (`AgentRoles` and
`AutoRun.agents`) already let plan, implement, review, fix and merge use different presets.
`context::decorate_agent` preserves the user's `--settings` and `-c` flags when adding the briefing.

- Claude (POSIX shell): `claude --settings '{"env":{"CLAUDE_AUTOCOMPACT_PCT_OVERRIDE":"60"}}'`.
  Use an explicit settings override because Claude's settings `env` takes precedence over an
  inherited shell variable.
- Codex: `codex -c model_auto_compact_token_limit=<tokens>`; replace `<tokens>` with a numeric
  threshold appropriate to the selected model's context window. Codex uses a token count;
  Claude uses a percentage. See the [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

For long-lived, resumed plan and implementation sessions, aim for compaction around 50–60% of
the context window to retain more reusable cached history. Short review, fix and merge sessions
usually finish before compaction; leave their provider default or choose a high threshold so a
review keeps the file details it is judging. These overrides need no dedicated Patchbay setting.
