### Keeping Rust and TS in sync

Types are mirrored by hand — there is no codegen:

- `status::Reply` ↔ `types.ts::Reply`; `TerminalEvent::Reply` and `Snapshot.replies` ↔ frontend reply events/snapshots. Stop replies are capped at `agent_hooks::REPLY_LIMIT`, well inside the journal's entry limit, so a long reply never costs its `Stop`. Session lists leave replies out and carry only `Snapshot.last_reply` (↔ `TerminalSnapshot.lastReply`); `reconcileSessions` reads a snapshot just when that names a reply the window hasn't seen, and `persistReplies` skips sequences it already persisted. `plans::Plan.saved_ms` ↔ `PlanText.savedMs`; `proposals::Proposal.saved_ms` ↔ `PlannerProposal.savedMs`, stamped by `proposals::read` from the file it read, never saved, and ignored when `apply` compares the proposal it was given.
- `crates/patchbay-core/src/model.rs` / `events.rs` / `devices.rs` (serde, `camelCase`) ↔ `apps/desktop/src/types.ts`
- Tauri command list in `src-tauri/src/lib.rs` (`generate_handler!`) ↔ wrappers in `apps/desktop/src/lib/ipc.ts` (Tauri converts camelCase args to snake_case params)
- The terminal event channel name `patchbay://terminal` appears in both `service.rs` (`TERMINAL_EVENT`) and `ipc.ts`.
- The Git invalidation channel `patchbay://git-dirty` appears in both `lib.rs` and `ipc.ts`.
- `usage::{Window, ProviderUsage, Usage, StatusLine}` ↔ `types.ts::{UsageWindow, ProviderUsage, Usage, StatusLineCapture}`; `usage_read`/`usage_status_line_check`/`usage_status_line_configure` ↔ `usageRead`/`usageStatusLineCheck`/`usageStatusLineConfigure`.
- `status::{SessionStatus, AgentReport, AgentState}` ↔ the same names in `types.ts`; `TerminalEvent::Status` ↔ the `status` event.
- `pty::Snapshot` ↔ `TerminalSnapshot`, `files::DirEntry` ↔ `DirEntry`, `git::{ChangedFile, ChangeKind, FileDiff, Review, Affected, Worktree}` ↔ the same names in `types.ts`. Terminal `started`/`exited` events and snapshots carry `startedMs`/`exitedMs`.
- `model::{MERGE_SCOPE, REVIEW_SCOPE}` ↔ the same constants in `types.ts`; `reviews::{ReviewRequest, Findings, Reviewer}` ↔ `ReviewRequest`/`ReviewFindings`/`ReviewerStatus`; `review_agent_start`/`review_read`/`review_prune` ↔ `reviewAgentStart`/`reviewRead`/`reviewPrune`; `session::Metadata.{branch, lane}` ↔ `SessionRecord.metadata.{branch, lane}`.
- `model::MAP_SCOPE` ↔ `types.ts` `MAP_SCOPE` (reserved `"@map"` scope of the dependency detection agent, one per project with terminal `link_proposals::MAP_TERMINAL` ↔ `MAP_AGENT_TERMINAL`); `link_proposals::{ProposedLink, Pending}` ↔ `ProposedLink`/`PendingLinks`; `detect_links`/`map_agent_start`/`map_links_read`/`map_links_clear` ↔ `detectLinks`/`mapAgentStart`/`mapLinksRead`/`mapLinksClear`; the `patchbay://map-links` event lives in `agent_commands.rs` (adapter) and `ipc.ts`.
- `model::PLAN_SCOPE` ↔ `types.ts` `PLAN_SCOPE` (reserved `"@plan"` scope), `model::PROJECT_SCOPE` ↔ `types.ts` `PROJECT_SCOPE` (reserved `"@project"` id for changed files no component contains).
- Session ids are opaque hashes of project id, component id and terminal key (`workspace::session_id`, `model::task_session_id` ↔ `types.ts` `sessionId(c, t, task?, projectId?)`); a task's terminal key is `{terminalId}@task-{taskId}` (`model::task_terminal`/`TASK_SEPARATOR`). Never parse an id: the service records `Metadata` (project, component, terminal, task) beside it, and the frontend's `sessionMetadata` map backs `parseSessionId`, `sessionTask` and `retask`.
- `stories::{Story, StoryKind, StoryStatus, StoryDraft, StoryPatch}` ↔ the same names in `types.ts`; `story_list/create/update/remove` ↔ `storyList/Create/Update/Remove` in `ipc.ts`. `plan_start` accepts a story id; only the backend reads its briefing text. `Kickoff::PlanStory` ↔ `{ kind: 'planStory' }`.
- `tasks::{Task, TaskDraft, TaskPatch}` ↔ the same names in `types.ts`; `task_*` commands ↔ `task*` wrappers in `ipc.ts`; `patchbay://tasks` (pop-out broadcast) lives only in `windows.ts`.
- `context::Kickoff::{ImplementPlan, FixFindings, Plan, PlanStory}` ↔ `types.ts` `Kickoff` (`{ kind, reviewSession?, subagents? }`) in `taskRootStart`/`planStart`/`startTerminal` (`plan` for Auto planners, `planStory` for story planners, through `plan_start` and `context::plan_session_spec(…, kickoff)`, which refuses other kickoffs; `AutoBrief::root_section` names a root agent's stage from its settled kickoff); `taskRootStart` sends the tagged object as `kickoff` and the review's session id as `reviewSession`. Only a `fixFindings` root launch receives review findings, instead of the shared plan and proposal, and its scope is the whole map rather than the highlights (extension context included); it records the reviewed branch in its `Metadata.branch`. When the frontend starts or restarts a root terminal whose record has a branch (or that this window launched as a fix, before the list reconciles), it sends `fixFindings` without `reviewSession` and skips saving plan drafts; the adapter's `recorded_fix` then reads that branch (listing sessions only for such terminals) as `context::Fix::Again`, and `context::root_handoff` briefs it with the same findings, or, once its branch moved or its findings are gone, starts it plainly with neither findings nor plan. A kickoff appends its prompt, and every root agent sets `resume_command` without one (also an Implement Restart, which sends no kickoff), so Resume and a Restart that resumes aren't re-prompted while a fresh start is, and Restart's fingerprint matches; the Shared plan section names when the plan was saved as an absolute UTC minute (`plans::saved_at`), never a relative age, and asks the agent to compare it with the current UTC time, so the briefing, which Codex may carry inline, and its inline-or-pointer form stay the same while the plan does. Saving a plan unchanged since the caller read it under the plans lock (the editor's checked Save, `capture`, `withdraw`) leaves an existing file (and save time) alone, though it still forgets applied assignments as any save does and, when a pending proposal is newer than the file, touches its mtime so the save still beats that proposal (`proposals::newer_plan`). A cut plan's note gives the whole file's size and exact version (mtime in nanoseconds), so the briefing changes with the plan past the cut. Codex's inline-or-pointer choice reserves room for the longest root kickoff (`Briefing.reserve`, measured on each root launch with the budget's own `command_len`), so it doesn't depend on which start it is. Kickoff prompts are bare arguments, so they avoid cmd-sensitive characters such as parentheses. The findings section holds only facts fixed by the findings (branch, base, reviewed HEAD), never their age or freshness, so the briefing, which Codex carries inline in its command, and with it Restart's fingerprint stay the same while the fix works. A handoff launch counts as started once its fresh terminal has any snapshot, so a lost reply never removes a running agent's tile. A kickoff launch rejects whenever it doesn't start (closing, a session reset), so a handoff never reports success for an agent that isn't running; its caller reports the error, so `startTerminal` shows no toast of its own. `review_fix_task` ↔ `reviewFixTask`. `context::task_root_session_spec` takes the optional kickoff and `context::root_handoff` picks the kickoff and the plan or the findings.
- `Kickoff::ImplementPlan.subagents` ↔ `Kickoff.subagents`: Implement only, clamped to `context::MAX_SUBAGENTS` (mirrored as `types.ts` `MAX_SUBAGENTS`, 8), and added only to the kickoff prompt, never the briefing. The limits are pinned in a Rust and a TS test; `types.ts` `SUBAGENT_COUNTS`/`isSubagentCount` are the only valid settings (the store setter and restore both check them). The per-project `implementSubagents` setting lives in the workspace layout.
- `plan_read`/`plan_write` ↔ `planRead`/`planWrite` (`plans::Plan` ↔ `PlanText`; `plan_write` replaces the file only while it holds `expected`); `terminal_start`/`component_context` take optional `peers` (`lib/plan.ts` `peersFor`).
- `reviews::{Severity, Severities, Verdict}` ↔ `Severity`/`Verdict` and `ReviewFindings.verdict`; the review briefing asks findings to start with `Verdict: clean | issues`, then `Counts: {"critical":…,"high":…,"medium":…,"low":…}`, and to tag each finding `[critical]`/`[high]`/`[medium]`/`[low]`. `reviews::verdict` reads both lines leniently (leading headings, blank lines, a BOM, Markdown emphasis; `Counts` optional, read only right after the verdict, blank lines aside, where unreadable totals give no verdict, and prose anywhere else), counts leading tags outside legends and code blocks, and takes the larger of reported and tagged totals per severity; any finding makes a clean verdict read as issues. Auto pauses on issues without a counted finding.
- `merges::MergeOutcome` ↔ `MergeOutcome`; `merge_outcome` ↔ `mergeOutcome` checks operation markers and uncommitted work (any in the source, tracked files only in the destination, so check artifacts don't hide a merge) before reporting integration from commit ancestry.
- `context::AutoBrief` ↔ `AutoBrief`; `plan_start`, `task_root_start`, `review_agent_start`, `merge_agent_start` accept optional `auto` (`startTerminal`'s `{ kickoff, auto }` options). Auto sections are backend-owned and precede extension context. Manual launches omit them.
- `git::Review.ahead` ↔ `Review.ahead`; optional `git_review.base` includes committed branch files for Auto inference and validation.

Additional topic interfaces belong to this same mirror contract:

- `stack_proposals::STACK_TERMINAL` ↔ `types.ts::STACK_AGENT_TERMINAL`; `stack_proposals::{ProposedTerminal, Pending}` ↔ `ProposedStackTerminal` / `PendingStack`; `stack_agent_start` / `stack_proposal_read` / `stack_proposal_clear` ↔ `stackAgentStart` / `stackProposalRead` / `stackProposalClear`; adapter `agent_commands.rs` `patchbay://stack-proposals` ↔ `lib/ipc.ts`. See [dependency and stack detection](dependency-and-stack-detection.md).
- `session::TERMINAL_RUNNING` ↔ `types.ts::TERMINAL_RUNNING`, matched by exact text when Auto classifies refused review launches. See [views and Auto](views-and-auto.md).
- `git_branches` ↔ `lib/ipc.ts::gitBranches` (`git::branches`); `merge_conflicts` ↔ `lib/ipc.ts::mergeConflicts` (`merges::conflicts`). See [Chat mode](chat-mode.md).
- `TerminalEvent::Reply.previous` ↔ frontend reply event `previous`; `status::Activity` and `HookEvent.{tool,target,file_target}` ↔ `types.ts::Activity`; `AgentReport.approval_pending` ↔ `approvalPending`; `session::prompt_forceable` ↔ `simpleComposer.ts::forceable` (which states Send anyway accepts; the service enforces it). See [Chat mode](chat-mode.md).
- `extensions.rs` registry/contribution types and `context::ContextSection` ↔ `types.ts`; extension backend commands ↔ `lib/ipc.ts`; `packages/extension-api/index.d.ts` defines the author API. See [extensions](extensions.md) for the command list and context-provider contract.
- `workspace::Workspace.settings` (opaque JSON) ↔ `types.ts::WorkspaceDocument.settings`; scheduler `background`, `pauseKind` and `pausedMs` are frontend workspace fields, with no new Rust command/type mirrors in Phase 1. See [frontend terminals](frontend-terminals.md) and [scheduler](scheduler.md).
- `service_retire` ↔ `lib/ipc.ts::serviceRetire`; preserve the service's `Hello` / `Shutdown` retirement wire format. See [data flow](data-flow.md).

Changing a model field or command means updating both sides.
