### Keeping Rust and TS in sync

Types are mirrored by hand — there is no codegen:

- `status::Reply` ↔ `types.ts::Reply`; `TerminalEvent::Reply` and `Snapshot.replies` ↔ frontend reply events/snapshots. Stop replies are capped at `agent_hooks::REPLY_LIMIT`, well inside the journal's entry limit, so a long reply never costs its `Stop`. Session lists leave replies out and carry only `Snapshot.last_reply` (↔ `TerminalSnapshot.lastReply`); `reconcileSessions` reads a snapshot just when that names a reply the window hasn't seen, and `persistReplies` skips sequences it already persisted. `plans::Plan.saved_ms` ↔ `PlanText.savedMs`; `proposals::Proposal.saved_ms` ↔ `PlannerProposal.savedMs`, stamped by `proposals::read` from the file it read, never saved, and ignored when `apply` compares the proposal it was given.
- `crates/patchbay-core/src/model.rs` / `events.rs` / `devices.rs` (serde, `camelCase`) ↔ `apps/desktop/src/types.ts`
- Tauri command list in `src-tauri/src/lib.rs` (`generate_handler!`) ↔ wrappers in `apps/desktop/src/lib/ipc.ts`, or in the `lib/` module that owns the feature (`chatTeams.ts`, `orchestration.ts`, `agentProfiles.ts`, `settingsBackup.ts`, `fileEditor.ts`, `windows.ts`, `sessions.ts`, `autoPower.ts`). Each command is invoked from one place; components never call `invoke`. Plugin commands are outside this list (`notifications.ts` calls `plugin:notification|notify`). `ipc.ts`'s `invoke` also runs provider-auth checks and adds the active `projectId`, so a module-owned wrapper skips both. (Tauri converts camelCase args to snake_case params)
- The desktop adapter and frontend name Tauri channels with matching `*_EVENT` constants. Adapter `service.rs` mirrors `ipc.ts` for `TERMINAL_EVENT` and `sessions.ts` for `SERVICE_EVENT` and `SERVICE_RETIREMENT_EVENT`.
- Adapter `lib.rs` mirrors `ipc.ts` for `FILE_ACCESS_EVENT`, `GIT_DIRTY_EVENT` and `BRANCHES_CHANGED_EVENT` (`watch::Change.branches`), `windows.ts` for `WINDOW_CLOSED_EVENT` (`CLOSED_EVENT` on the frontend), `nativeMenus.ts` for `MENU_ACTION_EVENT`, and `workspace.ts` for `QUIT_REQUEST_EVENT`. The smoke helper imports the menu channel from `nativeMenus.ts`.
- Adapter `agent_commands.rs` mirrors `tasks.ts` for `TASK_ACTIVITY_EVENT` and `ipc.ts` for `PROPOSAL_EVENT`, `MAP_LINKS_EVENT`, `STACK_PROPOSALS_EVENT`, `VALIDATION_PROPOSALS_EVENT`, `AGENT_QUESTION_EVENT` and `AGENT_QUESTION_CLOSED_EVENT`.
- The smoke harness mirrors `REPORT_EVENT` and `ACK_EVENT` in `smoke.rs` as `SMOKE_REPORT_EVENT` and `SMOKE_ACK_EVENT` in `smoke.ts`. The frontend editor close request channel is owned by `fileEditor.ts` (`EDITOR_CLOSE_REQUEST_EVENT`) and shared with `FileEditor.tsx`.
- Built-in detection provenance and device presets use `model::BUILTIN_SOURCE` (`"builtin"`), mirrored for detector labels in `lib/maintenance.ts`.
- `orchestration::chat::{WorkflowAction, WorkflowState, OwnerKind, LEAD_RECIPIENT}` ↔ the same names in `types.ts`. `lib/chatTeams.ts` uses the action and state unions in `ChatTeam.requests` and the state union in `TeamControl.requestState`. Owner kinds are stored in `orchestration.json`, which worktrees running different builds share, so each enum has an `unknown` (`#[serde(other)]`) fallback: an unrecognized value loads instead of failing the store, is never created, and `driveLeadRequests` leaves unknown actions unclaimed. The paired Rust and TS tests pin these wire spellings.
- `orchestration::chat::LEAD_BUSY_ELSEWHERE` ↔ `lib/chatTeams.ts` `LEAD_BUSY_ELSEWHERE`: the error a completion returns while the lead has work in other worktrees. `auto.ts` matches on it to retry quietly; paired tests pin the text.
- `usage::{Window, ProviderUsage, Usage, StatusLine}` ↔ `types.ts::{UsageWindow, ProviderUsage, Usage, StatusLineCapture}`; `usage_read`/`usage_status_line_check`/`usage_status_line_configure` ↔ `usageRead`/`usageStatusLineCheck`/`usageStatusLineConfigure`.
- `status::{SessionStatus, AgentReport, AgentState}` ↔ the same names in `types.ts`, including `AgentReport.limit_stopped_ms` ↔ `limitStoppedMs`; `TerminalEvent::Status` ↔ the `status` event.
- `pty::Snapshot` ↔ `TerminalSnapshot`, `files::DirEntry` ↔ `DirEntry`, `git::{ChangedFile, ChangeKind, FileDiff, Review, Affected, Worktree}` ↔ the same names in `types.ts`. Terminal `started`/`exited` events and snapshots carry `startedMs`/`exitedMs`.
- `pty::LaunchPurpose` ↔ `SessionRecord.spec.purpose` (`ordinary | chat`, missing defaults to ordinary); `task_root_start` / `taskRootStart` and `startTerminal` options accept the same purpose. `status::ChatStartup` (`pending | ready`) is mirrored inline by `TerminalSnapshot.chatStartup`, `SessionState.chatStartup` and the started/status terminal events; `Snapshot.chat_startup` uses the same wire field. Missing/null readiness means no bootstrap gate. Protocol 24 retains purpose across restart/resume/reset and exposes generation-bound Codex chat readiness; see [Chat mode](chat-mode.md).
- `model::{MERGE_SCOPE, REVIEW_SCOPE}` ↔ the same constants in `types.ts`; `reviews::{ReviewRequest, Findings, Reviewer}` ↔ `ReviewRequest`/`ReviewFindings`/`ReviewerStatus`; `review_agent_start`/`review_read`/`review_prune` ↔ `reviewAgentStart`/`reviewRead`/`reviewPrune`; `session::Metadata.{branch, lane}` ↔ `SessionRecord.metadata.{branch, lane}`.
- `model::MAP_SCOPE` ↔ `types.ts` `MAP_SCOPE` (reserved `"@map"` scope of the dependency detection agent, one per project with terminal `link_proposals::MAP_TERMINAL` ↔ `MAP_AGENT_TERMINAL`); `link_proposals::{ProposedLink, Pending}` ↔ `ProposedLink`/`PendingLinks`; `detect_links`/`map_agent_start`/`map_links_read`/`map_links_clear` ↔ `detectLinks`/`mapAgentStart`/`mapLinksRead`/`mapLinksClear`; the `patchbay://map-links` event lives in `agent_commands.rs` (adapter) and `ipc.ts`.
- `model::PLAN_SCOPE` ↔ `types.ts` `PLAN_SCOPE` (reserved `"@plan"` scope), `model::PROJECT_SCOPE` ↔ `types.ts` `PROJECT_SCOPE` (reserved `"@project"` id for changed files no component contains).
- Session ids are opaque hashes of project id, component id and terminal key (`workspace::session_id`, `model::task_session_id` ↔ `types.ts` `sessionId(c, t, task?, projectId?)`); a task's terminal key is `{terminalId}@task-{taskId}` (`model::task_terminal`/`TASK_SEPARATOR`). Never parse an id: the service records `Metadata` (project, component, terminal, task) beside it, and the frontend's `sessionMetadata` map backs `parseSessionId`, `sessionTask` and `retask`.
- `stories::{Story, StoryKind, StoryStatus, StoryDraft, StoryPatch}` ↔ the same names in `types.ts`, and `stories::{StorySource, ExternalItem, ImportReport}` ↔ `StorySource`, `ExternalStoryItem`, `StoryImportReport`; `story_list/create/update/remove/reorder` ↔ `storyList/Create/Update/Remove/Reorder` in `ipc.ts`. `stories::board_order` ↔ `lib/stories.ts` `boardOrder` and `stories::sibling_group` ↔ `siblings` share ordering and grouping rules; the golden board order is the same fixture in both test suites. `StoryStatus` includes `reviewing` and `merging`. `StoryPatch.expectedProgress` guards workflow saves against a changed status or worktree link. `stories::parent_status` ↔ `lib/stories.ts` `parentStatus` share Active/Closed rules covered by paired golden cases. `agent_bridge::Action::{Stories, StoryCreate, StoryUpdate}` ↔ the CLI’s `agent stories`, `agent story-create` and `agent story-update`. `plan_start` accepts a story id; only the backend reads its briefing text. `Kickoff::PlanStory` ↔ `{ kind: 'planStory' }`.
- `tasks::{Task, TaskDraft, TaskPatch}` ↔ the same names in `types.ts`; `task_*` commands ↔ `task*` wrappers in `ipc.ts`; `patchbay://tasks` (pop-out broadcast) lives only in `windows.ts`.
- `context::Kickoff::{ImplementPlan, FixFindings, Plan, PlanStory}` ↔ `types.ts` `Kickoff` (`{ kind, reviewSession? }`) in `taskRootStart`/`planStart`/`startTerminal` (`plan` for Auto planners, `planStory` for story planners, through `plan_start` and `context::plan_session_spec(…, kickoff)`, which refuses other kickoffs; `AutoBrief::root_section` names a root agent's stage from its settled kickoff); `taskRootStart` sends the tagged object as `kickoff` and the review's session id as `reviewSession`. Only a `fixFindings` root launch receives review findings, instead of the shared plan and proposal, and its scope is the whole map rather than the highlights (extension context included); it records the reviewed branch in its `Metadata.branch`. When the frontend starts or restarts a root terminal whose record has a branch (or that this window launched as a fix, before the list reconciles), it sends `fixFindings` without `reviewSession` and skips saving plan drafts; the adapter's `recorded_fix` then reads that branch (listing sessions only for such terminals) as `context::Fix::Again`, and `context::root_handoff` briefs it with the same findings, or, once its branch moved or its findings are gone, starts it plainly with neither findings nor plan. A kickoff appends its prompt, and every root agent sets `resume_command` without one (also an Implement Restart, which sends no kickoff), so Resume and a Restart that resumes aren't re-prompted while a fresh start is, and Restart's fingerprint matches; the Shared plan section names when the plan was saved as an absolute UTC minute (`plans::saved_at`), never a relative age, and asks the agent to compare it with the current UTC time, so the briefing, which Codex may carry inline, and its inline-or-pointer form stay the same while the plan does. Saving a plan unchanged since the caller read it under the plans lock (the editor's checked Save, `capture`, `withdraw`) leaves an existing file (and save time) alone, though it still forgets applied assignments as any save does and, when a pending proposal is newer than the file, touches its mtime so the save still beats that proposal (`proposals::newer_plan`). A cut plan's note gives the whole file's size and exact version (mtime in nanoseconds), so the briefing changes with the plan past the cut. Codex's inline-or-pointer choice reserves room for the longest root kickoff (`Briefing.reserve`, measured on each root launch with the budget's own `command_len`), so it doesn't depend on which start it is. Kickoff prompts are bare arguments, so they avoid cmd-sensitive characters such as parentheses. The findings section holds only facts fixed by the findings (branch, base, reviewed HEAD), never their age or freshness, so the briefing, which Codex carries inline in its command, and with it Restart's fingerprint stay the same while the fix works. A handoff launch counts as started once its fresh terminal has any snapshot, so a lost reply never removes a running agent's tile. A kickoff launch rejects whenever it doesn't start (closing, a session reset), so a handoff never reports success for an agent that isn't running; its caller reports the error, so `startTerminal` shows no toast of its own. `review_fix_task` ↔ `reviewFixTask`. `context::task_root_session_spec` takes the optional kickoff and `context::root_handoff` picks the kickoff and the plan or the findings.
- `plan_read`/`plan_write` ↔ `planRead`/`planWrite` (`plans::Plan` ↔ `PlanText`; `plan_write` replaces the file only while it holds `expected`); `save_chat_attachment` ↔ `saveChatAttachment` (raw image bytes as the body, the project id percent-encoded in the `patchbay-project` header; `attachments::save`); `terminal_start`/`component_context` take optional `peers` (`lib/plan.ts` `peersFor`).
- `reviews::{Severity, Severities, Verdict}` ↔ `Severity`/`Verdict` and `ReviewFindings.verdict`; the review briefing asks findings to start with `Verdict: clean | issues`, then `Counts: {"critical":…,"high":…,"medium":…,"low":…}`, and to tag each finding `[critical]`/`[high]`/`[medium]`/`[low]`. `reviews::verdict` reads both lines leniently (leading headings, blank lines, a BOM, Markdown emphasis; `Counts` optional, read only right after the verdict, blank lines aside, where unreadable totals give no verdict, and prose anywhere else), counts leading tags outside legends and code blocks, and takes the larger of reported and tagged totals per severity; any finding makes a clean verdict read as issues. Auto pauses on issues without a counted finding.
- `merges::MergeOutcome` ↔ `MergeOutcome`; `merge_outcome` ↔ `mergeOutcome` checks operation markers and uncommitted work (any in the source, tracked files only in the destination, so check artifacts don't hide a merge) before reporting integration from commit ancestry.
- `merge_branch_outcome` ↔ `mergeBranchOutcome` resolves destination state from live Git, checks for a saved restoration, and compares the clean source HEAD with the local destination branch tip if it has no checkout. Auto uses it for stage inference and merge monitoring. Both outcome commands record completion for eligible linked stories.
- `context::AutoBrief` ↔ `AutoBrief`; `plan_start`, `task_root_start`, `review_agent_start`, `merge_agent_start` accept optional `auto` (`startTerminal`'s `{ kickoff, auto }` options). Auto sections are backend-owned and precede extension context. Manual launches omit them.
- `git::Review.ahead` ↔ `Review.ahead`; optional `git_review.base` includes committed branch files for Auto inference and validation.
- `remote::{SyncStatus, SyncAction}` ↔ `types.ts::{SyncStatus, SyncAction}`; `git_sync_status`/`git_sync` ↔ `gitSyncStatus`/`gitSync` in `ipc.ts`, called only from `lib/gitSync.ts`. Both take a repository `git_history` lists for the worktree. See [Worktrees](worktrees.md).

Additional topic interfaces belong to this same mirror contract:

- `terminal_prompt` failures serialize as `PromptFailure { message, uncertain }`. The `terminalPrompt` wrapper turns them into `Error` objects with the message and the `uncertain` delivery flag for Chat and Auto. It keeps the original rejection as the cause. Tauri's plain-string rejections before dispatch count as refusals. Other unrecognized IPC failures count as uncertain.
- `stack_proposals::STACK_TERMINAL` ↔ `types.ts::STACK_AGENT_TERMINAL`; `stack_proposals::{ProposedTerminal, Pending (v2: checks, missingChecks, isolation, componentIds, auto), Isolation, IsolatedResource}` ↔ `ProposedStackTerminal` / `PendingStack` / `Isolation` / `IsolatedResource`; `validation_proposals::{ProposedCheck, MissingCheck, Pending}` ↔ `ProposedCheck` / `MissingCheck` / `PendingValidation` (legacy review only); `model::Instances` ↔ `Instances` (`Project.instances`, `SCHEMA_VERSION` 5 ↔ `projectFrom`); `tasks::Task.instance` ↔ `Task.instance`; `stack_agent_start` (`stackId`, `componentIds`, `auto`, `newDetection`) / `stack_proposal_read` / `stack_proposal_clear` ↔ `stackAgentStart` / `stackProposalRead` / `stackProposalClear`; `auto_setup::Outcome` ↔ `AutoSetupOutcome` (`auto_setup_report`), `auto_setup_set`, `worktree_setup_disable`, `graph_validation_cancel` (`task`); adapter `agent_commands.rs` `patchbay://stack-proposals` and `patchbay://auto-setup` ↔ `lib/ipc.ts`. See [dependency and stack detection](dependency-and-stack-detection.md).
- `session::TERMINAL_RUNNING` ↔ `types.ts::TERMINAL_RUNNING`, matched by exact text when Auto classifies refused review launches. See [views and Auto](views-and-auto.md).
- `session::WORKTREE_BUSY` ↔ `types.ts::WORKTREE_BUSY`, the prefix of an automated launch refused because a merge agent reserves its worktree; Auto pauses on it. `SessionSpec.manual` and `exclusive_cwd` are mirrored on the frontend record's `spec`.
- `git_branches` ↔ `lib/ipc.ts::gitBranches` (`git::branches`); `merge_conflicts` ↔ `lib/ipc.ts::mergeConflicts` (`merges::conflicts`); `merge_source_changes` ↔ `lib/ipc.ts::mergeSourceChanges` (`merges::source_changes`); `MergeRequest.commit_source` ↔ `commitSource`. See [Chat mode](chat-mode.md).
- `TerminalEvent::Reply.previous` ↔ frontend reply event `previous`; `status::Activity` and `HookEvent.{tool,target,file_target}` ↔ `types.ts::Activity`; `AgentReport.approval_pending` ↔ `approvalPending`; `AgentReport.questions` and `agent_hooks::{UserQuestion, QuestionOption}` ↔ `types.ts::UserQuestion`; `agent_questions::Pending` ↔ `types.ts::AgentQuestion` with the `agent_question*` commands and `patchbay://agent-question`/`-closed` events; `session::prompt_forceable` ↔ `simpleComposer.ts::forceable` (which states Send anyway accepts; the service enforces it). See [Chat mode](chat-mode.md).
- `extensions.rs` registry/contribution types and `context::ContextSection` ↔ `types.ts`; extension backend commands ↔ `lib/ipc.ts`; `packages/extension-api/index.d.ts` defines the author API. `extension_secret_set` ↔ `extensionSecretSet` includes the host list shown by the credential prompt. See [extensions](extensions.md) for the command list and context-provider contract.
- `settings_bundle::{Bundle, Imported}` ↔ `settingsBackup.ts` (`ImportedSettings`, including `profilesNeedingKeys`/`profilesMissingPrograms`); `settings_export`/`settings_import` ↔ the module-owned wrappers in `settingsBackup.ts`, which run their file dialogs in the backend; `settings_bundle::PORTABLE_SETTINGS` ↔ `PORTABLE_SETTINGS`, the only workspace settings exported and applied on import (everything else, such as `hookSources` and `mergeCleanupJobs`, stays on the machine). Add a new user preference to both lists.
- `workspace::Workspace.settings` (opaque JSON) ↔ `types.ts::WorkspaceDocument.settings`; scheduler `background`, `pauseKind` and `pausedMs` are frontend workspace fields, with no new Rust command/type mirrors in Phase 1. See [frontend terminals](frontend-terminals.md) and [scheduler](scheduler.md).
- `service_retire` ↔ `lib/ipc.ts::serviceRetire`; preserve the service's `Hello` / `Shutdown` retirement wire format. See [data flow](data-flow.md).

Changing a model field or command means updating both sides.
