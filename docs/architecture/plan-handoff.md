### Plan handoff

`plans.rs` — the plan a planner hands to implementation agents: one Markdown file per task (`main` without one) at `<git-common-dir>/patchbay/plans/<task>.md` (`tasks::store_dir`, beside `tasks.json`; task ids are checked so they can't escape the folder), written atomically (an existing file is left alone when a save under the lock finds its text unchanged) and capped at `PLAN_LIMIT` (`read` cuts longer files at a character boundary and says so); `tasks::remove` deletes the task's plan, best-effort. The planner belongs to the project, not a worktree: its sessions, plan (`main`) and proposal stay put when the active worktree changes (`captureLaunch` forces `task = null` for `PLAN_SCOPE`; `plannerSessionId` always uses that scope, and `plan_start`/`plan_context` and their IPC wrappers no longer accept a task), and Plan's Implement (`lib/planHandoff.ts`) hands them to the active worktree — offering a new worktree first on the project folder — by applying the proposal there (`proposals::apply(from, to)`, which preserves a saved plan newer than the pending proposal while applying its assignments and keeps the planner's own plan in step) or copying the nonempty project plan. An empty project plan must fail Implement even if the worktree has an older plan. Implement saves editor drafts before applying assignments, stops the planner, and starts a fresh root agent with an implementation prompt; launch failures propagate back to Plan, and the view switches to Implementation only after launch succeeds. Cancelling the New worktree dialog clears its pending follow-up callback. A pending proposal's components are outlined on Plan's canvas (`proposedScope`, UI only). Planner sessions get `PATCHBAY_PLAN_FILE` and a briefing line asking them to write the agreed plan there, plus `--add-dir` for the plans folder, created beforehand (`plans::dir`) and always added because agent sandboxes keep `.git` read-only unless it is a writable root itself; outside a repo the briefing leaves the line out. `session_resume` accepts the existing plans folder (`plans::existing_dir`, never created by the check) for any session. The Plan view's "Saved plan" editor reads and writes the same file, keeps unsaved planner edits per project at module level (so leaving the view keeps them), saves through `plans::write_if` and asks for a second Save when the planner rewrote the file since it was loaded, won't edit a cut plan, and is saved before Implement briefs agents. When an agent terminal starts (`terminal_start`, and the `component_context` preview), the adapter's `handoff_sections` adds "Shared plan" (`plans::section`: says when the plan was saved, as an absolute UTC time to compare with the current one, and whether it was cut, with the whole file's size and version) and "Working alongside" (`context::peers_section`: the other highlighted components and their links with this one, when the highlighted set holds it and others; pop-outs receive the highlighted set with `patchbay://tasks`); component agents also get `--add-dir` for those peers and, with a plan, the plans folder (`context::session_spec_with`). `briefing_sections` puts these backend-owned sections (and the task's) whole ahead of the extension context, which alone counts against `CONTEXT_BUDGET`. Neither changes session ids.

Claude’s opt-in status integration also captures native plans from `ExitPlanMode` hook payloads (`agent_hooks::plan_signal`), without reading provider-supplied paths or approving its dialog. `PreToolUse`/`PermissionRequest` capture a presented plan; `PostToolUse` records approval. A later turn event withdraws an unapproved presentation, restoring the previous plan only if the presented text is still current; editor changes are preserved. `plans::capture`/`withdraw` serialize these writes with the plan editor and proposal apply. Status is journaled first, then the hook uses a short bridge timeout so a disconnected desktop cannot hold up Claude. The bridge accepts captures and withdrawals only from a planner and checks its provider conversation to reject nested runs; subagent events are ignored. Repeated captures of unchanged text retain applied assignments.
