### Worktrees

`tasks.rs` — a task is a named piece of work on its own branch and worktree of the project repo, sharing the map. Tasks are per user, stored in `<git-common-dir>/patchbay/tasks.json` (shared by every worktree, never committed); `list` reconciles `branch`/`missing`/`current` with `git::try_worktrees` and fails rather than marking every task missing when `git worktree list` fails. `create` validates the branch (`check-ref-format`, no leading `-`) and base, then runs `git worktree add [-b]` into a free sibling folder `<repo>-<slug(branch)>` (the webview never picks the path); `attach` takes only a path `git::worktrees` lists; `remove` runs `git worktree remove` without `--force` (git refuses dirty trees) and keeps the branch. `remove_with_sessions` (behind `task_remove`) checks the worktree can go, has the session service stop the task's environments and sessions in every project (`TaskSessions::end_task` → `Request::EndTask`, under the operation lock so none can launch meanwhile), removes it, then forgets those sessions' records, which can't resume without the task; a failed forget doesn't undo the removal. Every window's `reconcileSessions` drops the state of sessions the service has forgotten (`withoutForgotten`). `create` checks the store is readable before running git and removes the new worktree (and branch) again if saving fails. Hot paths look tasks up with `stored` (no `git worktree list`), since `in_worktree` validates the path anyway. `project_in` moves a trusted, restricted `Project` into the task's worktree via `git::in_worktree`, dropping components outside that repo (and failing for required ones); `context_section` tells agents which task, branch and worktree they work in. The adapter's `for_task` looks the task up in the backend store (the webview sends only its id) for `terminal_start`, `plan_start`, `component_context` and `plan_context`, which then use `context::session_spec_for`/`plan_session_spec_for` (task in the session id and briefing file name) with extension sections read from the worktree; `git_status`/`git_changes` take `task`, `git_review`/`git_diff` the worktree path. `task_*` commands take the project id; `task_activate` adds that project's active task worktree to its watcher roots (`ProjectAccess.task_root`). Resuming a task's session re-checks its folders against the task's worktree. Extension terminals and the pop-out file tree still use the open worktree.

Frontend: `tasks`/`activeTask` are per-project UI state (`ProjectState`, never `dirty`) and `newTask` is global; `lib/tasks.ts` loads the list when a project's tab opens (`refreshTasks`) and again, quietly, when the watcher reports a branch change, and `followActiveTask` (main window) calls `task_activate` per project, and clears and refreshes Git badges only when a project switches task (not on tab switches). Every terminal list keys sessions with the active task (`TerminalPane`/`ValidationChips` take an explicit `task` override; extension terminals use `null`); `startTerminal(c, t, task?)` defaults to it. Attention lists every task's sessions and `revealTerminal` switches task. `WorktreePicker` lives in the rail's Worktree utility panel in every view and mode (with `copyPlan` while Full's Plan view is shown), the shared worktree switcher, and shows an overview of the Project folder and listed worktrees: labels and branches, attention, About component chips, changed and may-affect components via `git_review`, running terminals, collapsed editable notes, Review and Remove. `NewTaskDialog` ("New worktree": new branch or existing worktree, seeded from highlights, else the selection, by `lib/tasks.ts` `seedNewTask`) lives beside it in `components/tasks/`; Plan also offers "New worktree…". Clicking another worktree's row (outside its controls, chips, path and remove confirmation) switches to it; its title button is the keyboard way in; the trigger marks the active worktree's attention and, separately, other worktrees' (`attention.ts` `worktreeAttention`: terminals that want the user plus other worktrees' finished graph actions not yet seen; the store marks a worktree's actions seen in `seenActivities` in the same update that takes it off screen, however that happens: every store update, `useStore.setState` included, passes through `leaveWorktree`; `taskActions.ts` `unseenFinished` is the one test of a finished, unseen action). The picker shows the active worktree's first sentence (`shortTitle`, which ends a sentence only before a capital, so `e.g.` and `U.S.` stay), truncated by CSS, with its branch in the tooltip. The picker and Build's New task share one per-project read of the repo's worktrees (`lib/mainWorktree.ts`: whether there is a repo, and the main worktree's branch; the picker re-reads it on mount and open, the branch menus share their own listing through `readMainWorktrees`, Build reads it only if nobody has (`ensureMainWorktree`), and closing a project drops it and cancels a scheduled refresh). Each read is numbered when it starts, so only the newest one started applies. The watcher sends `patchbay://branches-changed` with the project id when a batch touches a `HEAD` (including linked worktrees' `.git/worktrees/<name>/HEAD`), a ref or `packed-refs`, or coverage is rebuilt; `App.tsx` settles each burst into one `scheduleBranchRefresh` (250ms) that re-reads the main worktree and the task list. File saves and window focus only refresh Git badges. UI text calls these worktrees; internal task types, commands and storage names stay the same. Review always shows the active task's worktree (no picker of its own; a worktree must be added as a task to be reviewed; switching drops the selected file, loaded review and a diff opened from findings) and shows validation chips for any worktree with a task.

Every merge starts through `lib/reviewAgents.ts::startMerge`: Review's dialog, the chat lead's `startMerge` request and Auto (see [Chat mode](chat-mode.md)). All flows select an existing local destination branch. The lead's request reports uncommitted source changes so it can ask for approval. With a clean source or an approved change list, `startMerge` resolves the destination and launches the merge agent. The reviewed worktree is always the source, including the primary checkout. `merges::resolve_destination` rechecks live source and branch state on submit, reuses a destination checkout, or creates a normal task with `tasks::create_existing` in the usual sibling folder. This path never creates a missing branch or activates the destination. The concrete `MergeRequest` continues through merge preparation, session tracking, outcome checks, and cleanup. A created checkout persists if agent launch fails, and retries reuse it. At the merge stage, Auto uses an existing checkout or calls the same resolver, then passes its pinned request to `startMerge` with `expectedSourceHead` for automatic merges. When Auto creates the destination checkout, the resolver records it for the same restoration on cleanup as a manual merge.

When the source has uncommitted changes, `MergeAgentDialog` lists them from `merge_source_changes` and offers **Commit and merge** in Review. The confirmed `git status --porcelain` entries travel as `MergeRequest.commit_source`; resolving and `merges::prepare` both refuse a list that no longer matches. Only then does the merge agent get the source worktree and its Git directories in `spec.dirs`, with a briefing that commits those changes on the source branch before merging the new HEAD. `resume_roots` treats `merge_source` appearing in `spec.dirs` as that grant, so such a run cannot resume once its source worktree is removed; ordinary merges still can. A dirty destination always blocks the merge.

Cleanup can restore the original checkout to the destination branch when Patchbay recorded ownership of the generated destination worktree. Its validation and open-project path checks run on a blocking worker using snapshots taken without retaining access locks. Restoration stops source sessions by their deepest registered worktree, preserving independent nested worktrees and retaining the original checkout's terminal history. Cleanup refreshes the shared frontend branch cache after success or partial failure, alongside tasks, sessions and Git badges.

Branch actions and restoration share `git::owning_worktree`, which assigns sessions to their deepest registered worktree even if a component's launch directory was removed. After confirmation and stopping writers, branch actions send `session::Request::BranchApply` (protocol 26): the service rechecks writers and applies the Git mutation under its launch operation lock, returning `NeedsStop` if a new writer appeared. Cleanup dialogs offer Retry validation after a failed preview, so clearing a dirty destination does not require dismissing the pending cleanup.

Merge cleanup uses `session::Request::MergeCleanup` (protocol 27) after stopping affected sessions. Under the same launch lock, the service validates cleanup again, refuses any new or still-stopping affected writer, and performs removal, restoration and branch deletion. Stops and graph-action cancellation happen before taking this lock; cleanup metadata retirement remains in the desktop adapter after the mutation. A merge agent runs in the destination, which cleanup keeps, so `CleanupPreview::owns_merge_agent` also claims `@merge` sessions by their `merge_source`: cleanup stops them with the source's sessions and forgets them once the source worktree is gone. Left running, one would reserve the destination indefinitely.

While a merge agent (`SessionSpec.exclusive_cwd`) runs, the service refuses automated launches into an overlapping folder with `WORKTREE_BUSY` and the agent's name. Auto pauses on it. In Chat, a delegation waits and a lead stage fails, telling the lead to ask the user about the merge agent.

A launch the person starts from a view is never refused. `SessionSpec.manual` is sent by `terminal_start`, `task_root_start` and `plan_start` for launches without a kickoff, Auto brief or story, including an interactive shell that starts on showing its pane. `session_resume` sends it from the Sessions panel and the Chat composer, and `ChatResume` sends it from `chat_continue` (the person's message to a team lead). It is decided per request, never taken from a stored record: an agent's resume, a Chat lead reset (`ResetConversation`) and a replacement lead all still wait. After such a launch or resume, `warnReservedFolder` asks `worktree_reservations` (`session::reservations`, the service's canonical overlap rule) for the merge agent, and the window shows a warning with **Stop merge agent**. Map, stack and extension launches stay automated.

A merge agent's own launch into a busy destination is refused with a different message ("A merge needs its destination to itself…"), so neither flow mistakes the blocker for a merge agent. A service of the previous build still refuses with "An exclusive session requires an unused worktree" (`LEGACY_WORKTREE_BUSY`) and ignores `manual` until sessions are restarted; a manual launch explains that.

Successful restoration marks its ownership record complete. The exact cleanup request can still be
retried, while branch-only status checks use live Git state when the source branch is checked out.
After an interrupted restoration has already switched the original folder to the destination
branch, branch-only status can use the pending record to verify the pinned refs.

## Syncing with the remote

The rail's Git panel (`components/git/GitPanel.tsx`, `lib/gitSync.ts`) syncs the active worktree's current branch through `remote.rs`. The repository is one that `git_history` lists for that worktree. `useSyncTracking`, mounted once by the rail, keeps the panel's repository while the map's folders are listed again, and reads ahead/behind from local refs when the scope changes, when the watcher reports moved refs (`branches-changed`), and on window focus. It never talks to the remote. Opening the panel fetches when the last fetch is more than a minute old. Fetch and push use the upstream's remote, otherwise `origin`, otherwise the only remote. When the push remote differs, Fetch also fetches it (and Pull tries to), so the push counts stay current. Fetch doesn't pass `--prune`, so the user's `fetch.prune` setting decides. Pull fetches and then runs `merge --ff-only`; the panel enables it whenever an upstream exists and the branch hasn't diverged, since the fetch can find commits the local count doesn't show yet. It refuses to run during a merge or rebase, and a diverged branch fails with a message instead of being merged or rebased. Push is never forced, and it only updates the remote branch of the same name. Like `push.default=simple`, it refuses a branch that tracks a branch with another name. It honours `branch.<name>.pushRemote` and `remote.pushDefault`. A branch without an upstream is published with `--set-upstream`. A configured upstream whose remote-tracking ref is gone is reported as `missingUpstream`, and Push refuses it rather than publishing it elsewhere. Push also refuses a branch that tracks a local branch (`branch.<name>.remote=.`), so it never replaces that upstream, and a branch with no commits yet; status on an unborn branch reports zero counts instead of failing. `SyncStatus` carries the push target (`pushTo`), why Push would be refused (`pushRefused`), and the counts against the target (`unpushed`, `pushBehind`), so the panel enables Push from the same plan `sync` follows. Pull asks first when terminals are running in the same checkout, including those of a task whose branch is checked out in the project folder. For another repository on the map (an external folder every worktree shares) it counts the terminals of components inside that repository, from any task. The rail badge counts commits against the push target, falling back to the upstream. An action error stays until the next action, so the status refresh that follows a failure doesn't hide it. Network commands cannot prompt: they set `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never` and BatchMode SSH (unless the user configured their own SSH command), and they stop after 120 s for a fetch and 10 minutes for a push or pull, whose hooks and checkout filters can be slow. A timeout stops Git's whole process group. Output is read for at most 2 s after Git exits, since an SSH connection master can hold its pipes open; whatever arrived by then is kept, so error messages survive. Credentials come from the user's Git setup, such as `gh auth setup-git` or ssh-agent. `git_sync` is main-window only and emits `git-dirty` and `branches-changed` afterwards.

The panel also holds the recent-commits graph, which moved there from Review and Chat's Changes. A chosen commit (`useCommitChoice`, keyed by project and active worktree, whose details read the worktree the history listed it from) opens in Review's diff pane, or in Chat's Changes when Chat mode is on. Choosing a changed file there clears it.
