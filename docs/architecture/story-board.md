### Story board

Navigation's Map / Stories toggle is a canvas sub-mode, persisted per project as `storyBoard` in the workspace layout; it never dirties the map or adds another View. The toggle also shows in Chat mode, where the board takes the place of the chat's map and Chat stays open (`setStoryBoard` switches `view` only outside Chat). The map stays mounted while the board is open. Epics contain features; features contain stories, and stories can also be unassigned. Items and acceptance criteria live in `stories.json` beside the per-user task store in the common Git directory, shared by worktrees and never committed. Features require an epic: keeping an epic's children during deletion requires moving its features first; deleting a feature without cascading leaves its stories unassigned.

Column headers stay pinned within the board while their card lists scroll independently. Epic markers are orange; feature markers are purple; story markers are light blue. Each column has its own status dropdown beside its title. Epics and Features offer All, Active and Closed. The Stories column offers All, Backlog, Active, Planned, Building, Review, Merge and Done. The filters are local to the mounted board, default to All, reset when the board reopens or the project changes, and never dirty the map. `lib/stories.ts`'s typed `filterStories` uses the same full-board derived statuses as card badges. The story column’s Active filter includes Planned, Building, Review and Merge. Each filter applies only to its column after epic/feature navigation, without hiding or including cards in other columns. Navigation and open editors retain their selections and unsaved fields when filters change or hide a card. Ordering is unchanged; column counts reflect filtered cards and the Unassigned count follows the Stories filter. Live status changes update the filtered cards. Empty filtered columns show “No matches for this status”; All retains the usual empty-state text. Creation and editor parent choices still use the full hierarchy.

`lib/stories.ts` owns hierarchy, status derivation and the Plan / Auto actions. A story planner uses the plan role and a backend-owned Story section (ancestors and descendants included). The project layout remembers `planStory` and `planStoryTerminal` for that session's Restart; a plain planner start preserves them, and only an explicit story start replaces them. Plan shows a dismissible pending-story chip; only the original terminal receives the Story briefing. New worktree in the editor or Plan links immediately at creation. Implement saves Building after launch and links the pending story to the worktree. An existing link to the same worktree keeps its `task_head`. Auto carries its pending story id through new-worktree creation and saves the run identity and stage after a successful start. Plan saves Planned after launch. These starts preserve saved Done but still save their worktree and run links, so a Done story follows new work.

The progress poll refreshes the board every five seconds and saves live stages for linked stories. Unfinished Auto runs map Scan and Plan to Planned, Implement, Validate and Fix to Building, Review to Review, and the merge gate and Merge to Merge. Outside Auto the newest running build, review or merge session by `snapshot.startedMs` supplies the stage; finished sessions leave the saved status alone. A later fix returns the story to Building. Idle worktree links keep the saved status, and the last saved stage remains available after worktree cleanup. Workflow status saves compare the story as saved on disk (`findStory` reads the file, since agent commands write it directly) and core skips only the status when it no longer matches; worktree and run links in the same save always apply. One story's failed save doesn't stop the poll's merge check. Confirmed merges and matching completed Auto runs save Done through core, and reopening that integrated work resumes it as Planned.

Epics and features display Active or Closed. A feature closes when all its stories are Done, and an epic closes when all its features are Closed. Either can also be closed by hand. Empty parents are Active unless manually closed. Editors let users close a parent explicitly, storing Done, or reopen a manually closed parent. Child-derived closure follows the board state; core `stories::parent_status` (used by `agent stories`) reads saved child statuses only, so it can lag a story its Auto run just completed. The parent's own workflow does not close it, and the parent editor says so. A card linked to a worktree also shows that worktree's Auto stage and status, for the item's own run or any unfinished one. A fresh branch at its base is not a completed merge. `smoke/stories.js` exercises creation, briefing, worktree linkage, goal prefill and returning to the map.

Board order is priority. Cards are dragged (or moved with Alt+↑/↓) only among their siblings, the cards a column shows together: an epic's features, a feature's stories (while that feature has an epic), and otherwise one unassigned group (`stories::sibling_group` ↔ `siblings`). Moving to another parent stays in the editor. Drag is off in a column whose filter isn't All, since hidden cards would make the order ambiguous. `lib/stories.ts` `reorder` computes the sibling sequence and `moveStory` shows it at once, then saves it, one save at a time per project so quick moves are stored in order, through `story_reorder` (core `stories::reorder`, which accepts only one complete sibling group and renumbers it), reloading the board if the save fails. Board refreshes don't apply while moves are saving, and a refresh that read the file before a save finished is discarded, so a poll never shows the old order. Core `stories::board_order` ↔ `lib/stories.ts` `boardOrder` walk each epic, its features and their stories, then unassigned stories, by `order`, `createdMs` and id; their paired golden tests share one fixture. `stories::next` is the first story in that order saved as Backlog with no linked worktree or Auto run. It uses saved status and linkage.

Chat supports `@` mentions of board items in the composer. The lead can read and edit the board, and uses the `story` setting on `startPlan` and `startAuto` to link work. See [Chat mode](chat-mode.md). A lead story plan uses `launchStoryPlanner`, the same launch as the board's Plan, without the replace prompt, since the lead's stage gate already refuses a running planner. It keeps only the story's components still on the map, falling back to the worktree's highlights when none remain. A lead story Auto uses `storyGoal` as its goal and `linkAutoStory` after the run starts, as the Auto panel does.
