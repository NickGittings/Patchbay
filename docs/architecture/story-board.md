### Story board

Navigation's Map / Stories toggle is a canvas sub-mode, persisted per project as `storyBoard` in the workspace layout; it never dirties the map or adds another View. The toggle also shows in Chat mode, where the board takes the place of the chat's map and Chat stays open (`setStoryBoard` switches `view` only outside Chat). The map stays mounted while the board is open. Epics contain features; features contain stories, and stories can also be unassigned. Items and acceptance criteria live in `stories.json` beside the per-user task store in the common Git directory, shared by worktrees and never committed. Features require an epic: keeping an epic's children during deletion requires moving its features first; deleting a feature without cascading leaves its stories unassigned.

Column headers stay pinned within the board while their card lists scroll independently. Epic markers are orange; feature markers are purple; story markers are light blue. Each column has its own status dropdown beside its title, offering All, Backlog, Active, Planned, Building, Review, Merge and Done. The filters are local to the mounted board, default to All, reset when the board reopens or the project changes, and never dirty the map. `lib/stories.ts`'s typed `filterStories` uses the same full-board derived statuses as card badges; Active includes Planned, Building, Review and Merge. Each filter applies only to its column after epic/feature navigation, without hiding or including cards in other columns. Navigation and open editors retain their selections and unsaved fields when filters change or hide a card. Ordering is unchanged; column counts reflect filtered cards and the Unassigned count follows the Stories filter. Live status changes update the filtered cards. Empty filtered columns show “No matches for this status”; All retains the usual empty-state text. Creation and editor parent choices still use the full hierarchy.

`lib/stories.ts` owns hierarchy, status derivation and the Plan / Auto actions. A story planner uses the plan role and a backend-owned Story section (ancestors and descendants included). The project layout remembers `planStory` and `planStoryTerminal` for that session's Restart; a plain planner start preserves them, and only an explicit story start replaces them. Plan shows a dismissible pending-story chip; only the original terminal receives the Story briefing. New worktree in the editor or Plan links immediately at creation. Implement links whichever planner hands off the pending story, skips a link already pointing to that task (preserving `task_head`), and clears the pending story after successful linkage. Auto carries its pending story id with the draft through new-worktree creation, linking it only after a successful run start. Cards derive review and merge stages from unfinished Auto stages or the newest matching review/merge/root session by `snapshot.startedMs`; a later fix returns to Building. These display stages do not change stored `StoryStatus`. Cards follow live worktrees, finished Auto runs and verified recorded merges; parent statuses roll up from children, while explicit Done stays Done. A card linked to a worktree also shows that worktree's Auto stage and status, for the item's own run or any unfinished one. A fresh branch at its base is not a completed merge. `smoke/stories.js` exercises creation, briefing, worktree linkage, goal prefill and returning to the map.

Board order is priority. Cards are dragged (or moved with Alt+↑/↓) only among their siblings, the cards a column shows together: an epic's features, a feature's stories (while that feature has an epic), and otherwise one unassigned group (`stories::sibling_group` ↔ `siblings`). Moving to another parent stays in the editor. Drag is off in a column whose filter isn't All, since hidden cards would make the order ambiguous. `lib/stories.ts` `reorder` computes the sibling sequence and `moveStory` shows it at once, then saves it, one save at a time per project so quick moves are stored in order, through `story_reorder` (core `stories::reorder`, which accepts only one complete sibling group and renumbers it), reloading the board if the save fails. Board refreshes don't apply while moves are saving, and a refresh that read the file before a save finished is discarded, so a poll never shows the old order. Core `stories::board_order` ↔ `lib/stories.ts` `boardOrder` walk each epic, its features and their stories, then unassigned stories, by `order`, `createdMs` and id; their paired golden tests share one fixture. `stories::next` is the first story in that order saved as Backlog with no linked worktree or Auto run. It reads saved statuses, not the derived Review/Merge badges.

Chat reaches the board in two ways (see [Chat mode](chat-mode.md)): `@` mentions of epics, features and stories in the composer, and the lead's `agent stories` command with the `story` setting on `startPlan` and `startAuto`. A lead story plan uses `launchStoryPlanner`, the same launch as the board's Plan, without the replace prompt, since the lead's stage gate already refuses a running planner. It keeps only the story's components still on the map, falling back to the worktree's highlights when none remain. A lead story Auto uses `storyGoal` as its goal and `linkAutoStory` after the run starts, as the Auto panel does.
