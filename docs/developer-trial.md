# Two-week developer trial

Run after editor navigation and reviewed map maintenance land and participants can install
a validated build on their platforms. The trial has not been conducted by the automated
implementation or smoke checks.

Recruit developers who regularly work across multiple repository components, use task
worktrees, and run Claude or Codex interactively. Use their preferred editor and real projects.
Record the build commit and platform for each participant so failures can be reproduced.

## Schedule

| When      | Activity                                                                                                                                  |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Day 1     | Install, open an existing project, choose an editor, create/activate a task, open a file, review a rescan preview. Record setup friction. |
| Days 2–6  | Leave use voluntary. Record return dates and the work the developer chose Patchbay for. Separate requested test sessions.                 |
| Day 7     | Brief check-in: navigation accuracy, map proposals, interrupted/resumed work, and reasons for returning or leaving.                       |
| Days 8–13 | Continue voluntary use with the same build, or record the commit when applying a necessary fix.                                           |
| Day 14    | Review return frequency, completed workflows, failure reports, and each participant's intent to keep using Patchbay.                      |

## Record

Use pseudonymous participant IDs in a local spreadsheet. Each session row contains:
participant ID, date, build commit, platform, voluntary/requested, workflow attempted,
completion, problem encountered, and brief feedback. Do not collect terminal content,
repository code, conversation IDs, or provider credentials to measure adoption.

Report the participant count and number returning voluntarily at least once after Day 1.
Also report how many returned in the second week and the number of voluntary use days per
participant. Keep requested smoke/test sessions out of these counts. List setup failures and
reasons for non-return beside the counts; a small trial does not establish broad adoption.

Use the results to decide which navigation, maintenance, status or environment failures need
fixes before a wider release. Preserve individual workflow reports so the team can distinguish
incorrect routing from a missing launcher, denied folder, provider setup issue, or failed Docker command.
